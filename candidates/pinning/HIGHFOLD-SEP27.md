## Mathematical representation

The CPU co-grinder evaluates Q+ = A + z B, followed by the inherited recovery work. The baseline folds A into the lowest unsigned window and uses ten signed higher windows for the large 4 GiB table. The top signed window must accommodate a carry beyond the 256 input bits. A conventional ten-window alternative spends approximately 18 GiB on table records.

This candidate instead stores the fixed-A table as physical window zero at the HIGHEST position. The nine lower signed widths are [25,25,25,26,26,26,26,26,26], in ascending bit position. They cover bits 0 through 230. The high unsigned window has width 25 at bit position 231. It has 2^25+1 records, including the single extra final-carry record. Each lower signed table has 2^(width-1) records representing magnitudes one through the half radix; zero uses the inherited zero code rather than a table entry.

For a lower window, v = raw + incoming carry, negative = v > half, and signed digit = v - negative*radix. The outgoing carry is negative. Summing the weighted lower digits telescopes to z_low - final_carry*2^231. The high record index is (z >> 231) + final_carry, which restores the original integer exactly. Ties remain positive. A zero magnitude after a full-radix value still propagates carry; the final lower signed digit must not use the old top-window unsigned exception. The extra high record is mandatory for all-max and other boundary inputs.

The total is 285212673 records, each 64 bytes: 18253611072 bytes, or 17 GiB plus 64 bytes. This saves one GiB minus 64 bytes compared with the conventional 18 GiB ten-window representation. Relative to the actual promoted 4 GiB eleven-window table, memory and record count increase by approximately 4.25 times. The representation removes one signed affine chain stage on the CPU search path; it does not remove any GPU search stage. Memory savings against 18 GiB are not an additional arithmetic saving against that ten-window alternative.

## Production changes and dispatch

Only cpu_cogrind.h and cg_table.h implement the new behavior. The named highfold layout uses physical slot zero for the high unsigned A-folded table; the existing scalar and AVX2 consumers already initialize from physical slot zero and process subsequent signed slots, so their point-add loops need no new representation. Each scalar and AVX2 recoder processes the lower slots in ascending bit position, then stores the high index plus the final carry. The old layouts preserve their original top-window mask and carry behavior. The vector comparison operands remain small enough for the inherited signed 64-bit comparisons, and the four 32-bit packed indices retain the inherited lane order.

Automatic selection chooses highfold only when the existing host and cgroup memory availability calculation reports at least 32768 MiB. Unknown or smaller memory retains the original selection thresholds. The allocation fallback list recognizes highfold and steps down to xlarge, large, medium, small and tiny if its mapping fails or its headroom check no longer passes. This is a conservative availability guard, not proof that future resident memory cannot be exhausted: inherited MAP_NORESERVE mapping success does not prove that physical pages fit under external concurrent pressure. The inherited CPU controller, affinity policy and one-way worker shedding remain unchanged.

Table construction uses 4096-point rows instead of 256, and 65536-entry segments instead of 4096. Each segment still obtains an independently derived OpenSSL starting point. Subsequent rows add the same precomputed 4096*G_j step. The high table's last segment contains just one record, so row initialization only constructs the required records and does not evaluate thousands of unused point additions. Explicit allocation checks were added for the enlarged precomputed-point scratch; a failed precomputation returns before copying incomplete points. Opposite-point and zero-denominator failures still mark the table bad and prevent CPU workers from starting. The final OpenSSL spot check and all verifier-facing output logic remain intact. GPU kernels and the embedded carrier are byte-identical to the baseline.

## Focused checks and their limits

A source-linked Python word recoding and SIMD packing model checked 50111 integers including full-width random values, half-radix boundaries, carry-producing zero digits and all-max input. All reconstructed the original integer and all table indices stayed in bounds. Fifty-two cases required the extra high record. A negative mutation suppressing the last signed carry produced 25117 out-of-table indices; integer reconstruction alone would not catch that representation mistake. These are independent Python models and source anchors, not execution of the C++ intrinsics.

The independent secp256k1 affine model previously checked seventy A+zB cases, including z=0,1,n-1,n and all-max, plus a constructed final infinity. The batch-builder model compared 4096 precomputed points with a separate affine recurrence and 4096 A-folded row points with independent affine additions. Doubling, opposite points and a synthetic zero-ordinate failure branch were covered. The larger segment geometry is checked separately: 4353 segment initializations and 69633 rows cover every highfold record exactly, with no extra write in the one-record tail. This is not construction of the full 17 GiB table or a native OpenSSL/CUDA run.

The source comparison checks all unaffected official blobs, the protected manifest, GPU source and carrier identity, the declaration order for the memory-availability helper, the changed allocation list and the actual recoding anchors. Git diff whitespace checks and editable-path scope checks precede freezing. Source hashes and model results are archived with the candidate. No external pending source has been integrated without permission to inspect it.

## Cost accounting and why this remains an experiment

For n nonexceptional affine additions the existing batch operation uses 5n-3 multiplications plus n squares and one inversion. The unchanged scalar inverse addition chain uses 15 multiplications and 255 squares. Thus the approximate per-point batch arithmetic changes from 5.046875M+1.99609375S at n=256 to 5.0029296875M+1.062255859375S at n=4096. Enlarging the batch reduces inversion overhead, but the 4.25-times larger highfold table still has about 3.66 to 3.89 times the baseline construction arithmetic if a square costs between one and one-half multiplication. Those ratios are operation bookkeeping, not execution timings.

The enlarged segment reduces OpenSSL starting-point initializations from 69633 at 4096-entry segments to 4353 at 65536-entry segments for the highfold layout. That can reduce setup cost independently of the inversion arithmetic. Scratch per builder grows from 73728 bytes to 1179648 bytes, and ten precomputed point windows consume about 2.5 MiB. Cache pressure, longer prefix-product dependencies, stop latency and coarser load balancing can regress performance. The larger table also increases resident-memory demand and can reduce lookup locality. The CPU path is a small part of aggregate throughput, so a saved CPU stage is not a prediction of a one-percent aggregate gain.

The purpose of this official submission is to test this coherent representation-plus-construction change, not to claim it is already faster. The remote result must decide build compatibility, runtime verification and aggregate throughput. A rejected result will not justify an identical-source retry or an unsupported attribution to a particular host. We retain the original GPU path and independent publication verification, and will use the official outcome to decide whether the new table layout, builder policy or both should be removed in a later fresh candidate.
