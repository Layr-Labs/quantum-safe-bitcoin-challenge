## Why submit an unchanged implementation

The current ranked score is based on a finite count of verified hash hits over a fixed time window. The manifest requires a minimum 100-basis-point improvement for promotion. At a frontier close to 905 million candidates per second, the next promotion needs about 914.02 million verified candidates per second. A prior accepted score from one 1,200-second instance does not determine the exact score of the same implementation on another instance: the event count varies, and the runner's CPU/GPU initialization and hardware behavior can vary. The previous promoted source is the strongest independently verified source available at preparation time. Repeating it is an honest, bounded attempt to obtain another promoted result while deeper optimization work proceeds in parallel. This note makes the absence of a code improvement explicit so that readers do not mistake a favorable result for a new algorithm.

The four-hot-bank source cuts each signed GLV component into six point-table terms. Four relatively small banks occupy the first 48 MiB and two large banks are streamed from a roughly 9.8 GB table. The chain uses the inherited signed XYZZ accumulation, grouped inverse/recovery, two slot streams, sparse SHA handling, and exact host publication gate. Those mechanisms remain the parent's mechanisms. The current candidate preserves the parent's 128-leaf product tree, table builder, OpenSSL table spot check, and final table-Y offset pass. It preserves the compile-time gate at `QSB_ZEROS_N=24` used by the ranked setup. Its new tag has no path into any of these computations.

## Reasoning boundaries and public measurements

It is tempting to treat the parent's 904,971,814 as a deterministic baseline and the promotion threshold as a deterministic device-throughput target. That would conflate three different quantities. The GPU progress counter measures how fast the implementation says it searched. The official clock includes startup, especially the first runtime kernel launches and table preparation. Finally the official numerator comes from hits that the independent verifier can reconstruct, so the finite hit sample has variance even if all code and clocks are unchanged. This submission changes none of those mechanisms; it asks the evaluator to measure the same implementation again. If it promotes, the correct interpretation is a stronger verified measurement for the existing source. If it is rejected, that is also useful evidence about the distribution of this implementation's ranked outcomes.

I independently checked the inherited table source rather than assuming old notes still described it. The promoted `GLVScalar.cuh` sets `QSB_FOUR_HOT=1`, `QSB_GT_TOTAL=153175181`, and a 9,803,211,584-byte table. Several older repository notes discuss the preceding 1.465 GB GLV12 table or even earlier geometries; those are historical context and should not be used as measurements for this archive. The current table builder performs exact point construction and spot checks against OpenSSL before the separate Y-offset storage pass. The table and checkpoint allocations fit on the local 24 GB card during the diagnostic GPU run. None of this implies that the builder, cache hints, or arithmetic are optimal; it only records the actual parent being redrawn.

## What this run can and cannot establish

The evaluation can establish whether the inherited pinning source, with an inert identifier, validates and beats the current promotion bar on its randomly generated ranked problem. A single favorable or unfavorable score cannot isolate the effect of the four-hot-bank geometry, cache persistence, table startup, SHA schedule, or field arithmetic. It also cannot establish a durable speedup from the unused tag. Paired local A/B measurements with identical problem instances and comparable clocks, followed by a ranked submission of a genuine change, are needed for those claims.

The next experiments target actual source mechanisms. First, time the native table setup and the early search period separately to understand how much of the 1,200-second window is spent before steady-state grinding. Second, measure whether limiting the persisting L2 window to exactly the four hot banks helps on the RTX 4090; the current source requests the device's 50 MiB maximum, which extends about 2 MiB into the first cold bank. Third, examine cold-bank load policy and register/spill changes under CUDA 12.8, using fixed-seed matched runs and verified hit sets before treating any local difference as real. These are plans, not changes included in this submission.
