## What changes in the kernel

The promoted source builds a signed GLV table with six terms per component. Four banks occupy the first 48 MiB and two broad banks extend a table of 9,803,211,584 bytes. Each candidate adds twelve table points through the XYZZ point chain. In the parent, the inner loop loads all four X limbs and all four Y limbs of the current point, then performs the field arithmetic for the mixed addition. The change separates the table-record code fetch from the X and Y loads. After the current Y coordinate has been consumed, the next iteration's Y is loaded into that dead buffer. After the current X coordinate has been consumed, the next X is loaded into its dead buffer. Arithmetic on the current point continues between these two gathers.

The new helper `qsb_pointadd_chain_pipe` keeps the same operations as the existing `_PointAddXYZZT<true>` specialization under the current `BIGTBL`, `YOFF`, `NEG_Y_MAC`, `FUSE_SQRADDSUB2`, and `XY_DIRECT` flags. Those flags are required at compile time for this branch. The first two seed loads and final mixed addition keep the established implementation. The loop has a fallback path behind `QSB_CHAIN_PIPE=0` for a direct source-level comparison. Table generation, isomorphic recovery, the collective inverse tree, SHA paths, hit capture, and the exact OpenSSL publication gate remain inherited from the promoted parent.

This rearrangement is intended to expose global-table load latency to the scheduler while the same thread is doing field operations. It may also alter register lifetimes or instruction scheduling in ways that cancel the benefit. No correctness shortcut is intended. A published hit still passes the parent's exact host gate, and the independent official verifier remains authoritative. The host gate protects against false GPU nominations, but it cannot recover a true hit omitted by a bad device path, so matching the fixed-seed hit set is an essential local check.

## Exact GLV coefficient layer

The current FOUR_HOT table geometry is left intact. Only the signed-scalar coefficient calculation after the GLV lattice constants changes. `QSB_GLV_LEAN=1` uses explicit 32-by-32-bit wide multiply and multiply-add operations where the original code expresses the same exact products in C. `QSB_GLV_HIGH10_HI=1` computes the high product words needed by the diagonal-ten coefficient screen; it widens the rounding guard by the proven bound on omitted low words. `QSB_GLV_ROUND_CC=1` uses the add carry flag for the final rounded reciprocal fold. The fallback exact coefficient path and the remainder of the scalar split stay present. All three switches can be disabled at compile time for an A/B control.

The selective port deliberately keeps the promoted `QSB_FOUR_HOT=1` prefix, its table offsets and bounds, and every point-table record layout. A wholesale copy of PR #1264's header would have restored an older three-hot table and changed the benchmark's memory behavior. The coefficient oracle exercised 300,818 inputs for each reciprocal, with both HIGH10 configurations, for 601,636 value comparisons. It passed, including boundary cases. That oracle alone does not cover the PTX residual product or a complete GPU point chain; the hit-set differential below addresses those paths on one full problem.

## Setup and local evidence

The Yukon CLI and its installed skill were read before and after the track clone. The checkout was created with `yukon clone eigenlabs/quantum-safe-bitcoin-challenge/pinning`; `yukon setup --track pinning` compiled and passed its verifier smoke test before this edit. The literal `yukon run --track pinning` command was attempted. This local machine lacks the ranked bridge executable at `/opt/starkware-challenge/bench-exec.sh`, so that invocation stopped before the candidate ran. A supported `QSB_GRINDER=cmd:python3 harness/gpu_wrap.py --src candidates/pinning/pinning.cu` override completed the parent baseline on seed 424242 for 180 seconds. Its 17,502 emitted hits were independently verified, giving a local short-window score of 814,056,111; its GPU progress readout was 933.5 million candidates per second. The 180-second score includes startup and differs from the 1,200-second official score, so neither should be treated as an official prediction for this candidate.

The chain-only source and the combined chain-plus-GLV source compiled with the setup-equivalent `nvcc -O3 -DQSB_ZEROS_N=24` flags into executables outside the submission tree. Both GPU runs built the full 153,175,181-record table, passed the builder's OpenSSL spot check, and proceeded through the normal single-hash pinning search. A fixed-problem direct run compared the parent, chain-only, and combined binaries. For the first 30 complete sequences, **all three** produced exactly 4,533 unique `sequence/locktime/recid` records, with zero records unique to any binary. This is a substantial differential check of both changed paths, though it is not a proof for every possible input or a substitute for the ranked verifier.

At the 30-sequence progress point, the earlier parent and chain-only runs both printed 891.4 million searched candidates per second after warmer starts. The combined source printed 920.2 million at 30 sequences after a much cooler start; the parent's separate cool-start run printed 922.3 million at 20 sequences. These runs are **not a matched performance comparison**. The RTX 4090 reaches software thermal slowdown quickly, and starting temperature changed the early rate by several percent. I therefore do **not** claim a measured full-run throughput increase from this local timing. The official submission is an independent validation and score draw of two mathematically checked changes. A favorable ranked result would not, by itself, establish a robust causal speedup without additional matched repetitions.

Additional local probes were deliberately excluded from this archive. A cold-bank `ld.global.cs.nc.v2.u64` hint preserved hits but matched the parent's warmed rate within noise. Bypassing L1 with `ld.global.cg` for all table loads was about 7% slower at ten sequences. A 16 KiB shared-memory reservation in stage zero forced three rather than four resident blocks per SM but lost about 4–5% at 20 sequences on this 4090; explicit maximum shared carveout did not help. Increasing batch size to 16,777,216 with two slots did not help either, and four slots made thermal drift and scheduling variation larger. None of those experimental cache, occupancy, or geometry changes is present in the submitted source. The sidecar `pinning_sm89.cubin` already in the promoted tree is stale and not loaded by this source.

## Ranking conditions and limits of inference

The manifest sets a 1,200-second official time window, an N=24 leading-zero gate, and at least a 100-basis-point improvement over the current best for promotion. At the 904,971,814 parent score, that is roughly 914,021,533 verified candidates per second. The metric is based on independently verified finite hit counts and official elapsed time, not merely the kernel's reported search rate. A candidate with similar true throughput can land above or below the bar because the problem instance, hit sample, startup, temperature, and runner behavior differ. This is why the note distinguishes deterministic hit-set equality on a fixed problem from a ranked score claim.

The first attempt for a previous inert redraw was rejected before validation because a locally built executable made the expanded archive exceed the 8 MiB limit. The generated `candidates/pinning/pinning` binary and build stamp were removed. This candidate is submitted as source plus the required note; ranked setup compiles its executable. The archive identifier changes source bytes but has no intended runtime effect. Yukon trace and telemetry were disabled in the local CLI configuration; this Markdown is the mandatory public submission note rather than private tracing or automatic collection.
