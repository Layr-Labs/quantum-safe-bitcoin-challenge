# Pinning submission D — exact SHA addition scheduling on the GLV control

## Scope and source

This archive changes only the pinning track. It starts from the promoted FOUR_HOT GLV12 pinning source and the exact signed-GLV coefficient port used in my C submission, `859ea879-804f-4f00-b0ff-52a2cdc0383b`. That C validation was still in progress while this note was prepared. The promoted score observed at preparation was 904,971,814 verified candidates per second, and the 1% promotion threshold was 914,021,533. An earlier combined chain-pipeline-plus-GLV submission, `64cf37f1-e704-45e9-ae02-3e3fe34413ec`, was fully verified at 906,504,249 with 129,857 valid hits in 1,201.6706 seconds, but rejected below that threshold. This D package retains C's `QSB_CHAIN_PIPE=0`, four-hot table geometry, GLV coefficient arithmetic, host OpenSSL gate, slot scheduling, and recovery equations. It does not add a table, change a search interval, or relax hit publication.

The only active difference from C is `QSB_SHA_ALU_ADD=1` in `sha_pinsha.cuh`. `QSB_CODEX_DRAW_20260924_D` near the start of `pinning.cu` is an unused source marker. It has no device or host runtime effect. The marker makes the archived source distinguishable from C in the public record. The prior C marker remains because the code still includes that lineage. The native cubin sidecar inherited from the promoted source is not loaded by this candidate. Generated executables and local benchmark outputs are excluded from the intended submission archive.

The C coefficient code came from the public ItlaStudent GLV arithmetic in [pinning PR #1264](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1264), adapted to the promoted four-hot geometry. The three switches remain `QSB_GLV_LEAN=1`, `QSB_GLV_HIGH10_HI=1`, and `QSB_GLV_ROUND_CC=1`. The donor note also credits kaankolcu and Portablelle for earlier lean-multiply work. The coefficient transformation was tested separately against exact reciprocal arithmetic for 601,636 values and by GPU hit-set comparisons. This D experiment does not claim to invent or modify that arithmetic.

## Exact change and hypothesis

The new `QSB_SHA_ALU_ADD` switch feeds a zero from constant memory into selected SHA-256 additions in the common pinning SHA helper. Addition modulo 2^32 is unchanged: `d + t1 + 0 == d + t1`, and the rolling message-schedule additions have the same identity. The constant-bank operand prevents ptxas from choosing `IMAD.IADD` for those two-operand additions, allowing `IADD3` on the integer ALU pipe. This is an instruction scheduling experiment, not an approximate hash. All 64 SHA rounds, message words, digest checks, and the exact host OpenSSL verification remain as before. The helper also participates in the stage-2 pubkey hash, so the benchmark measurement, rather than a static stage-0 count alone, decides whether the shift helps overall.

The stage-0 fixed-base chain contains many integer multiply-add instructions. The scheduling hypothesis was that moving a small set of independent SHA adds to the other pipe would relieve the multiply-add issue path without adding instructions or spilling registers. The effect is expected to be small because the SHA work is only a portion of stage 0. The change is reversible with `-DQSB_SHA_ALU_ADD=0`, which compiles the C path. The `pin_zero_add` symbol is initialized to zero in the CUDA source. The compiled experiment was checked by full search results, so a hypothetical constant-memory setup mistake would be visible as a mismatched hit set.

## Build and static inspection

I compiled C and D from the same pinning source under CUDA 12.8. The native diagnostic build used `nvcc -O3 -arch=sm_89 -DQSB_ZEROS_N=24 -Xptxas=-v` and linked `-lcrypto -lm`. The stage-0 specialization stayed at 122 registers, 12,288 bytes of shared memory, zero stack frame, and zero spill loads or stores. Stage 2 stayed at 64 registers and zero spill loads or stores. A `cuobjdump --dump-sass` comparison of the stage-0 specialization showed `IMAD.IADD` occurrences fall from 201 to 51 and `IADD3` occurrences rise from 1,375 to 1,528; the static function-section line count remained 13,222. Stage 2 changed from 44 to 20 `IMAD.IADD` occurrences and from 469 to 497 `IADD3` occurrences, with 16 more static section lines. These are compiler counts, not executed instructions or a performance proof.

The exact setup-style command `nvcc -O3 -DQSB_ZEROS_N=24 ... -lcrypto -lm` also compiled and ran. On this local toolchain it emits the compute-52 PTX route and the NVIDIA driver JITs it for the RTX 4090. This matters because the ranking setup uses that command rather than my native diagnostic `-arch=sm_89` flag. The switch is active in both builds. The four-hot GPU table builder completed in about 0.7 seconds on the native tests, its OpenSSL spot check passed, and neither build reported a CUDA error. The existing `QSB_HOST_GATE=1` remains mandatory and filters every published hit through exact OpenSSL recovery and hashing.

## Local GPU A/B evidence

The local test machine has one RTX 4090. I used the same problem file, sequence range, zero-bit target, two-slot pipeline, and 30-sequence stopping rule for each pair. Sequence 30 means 37.338 billion examined candidates. Search progress was captured through line-buffered stdout; the test process was then stopped. Because work for sequence 31 can be queued when the sequence-30 progress line appears, total rows in the truncated result file can differ. Restricting records to sequences 0 through 29 gives exactly 4,533 hits for C and D, with the same `(sequence, locktime, recid)` records. The extra few rows after the cutoff are not part of the comparison. This hit-set check covers a large real search sample, but it does not prove all possible field inputs; the unchanged exact OpenSSL publication gate remains the final correctness protection.

| Local build and pair | Start temperature | C at sequence 30 | D at sequence 30 | Difference |
|---|---:|---:|---:|---:|
| Native sm_89 | 50 °C / 49 °C | 902.5 M/s | 904.0 M/s | +0.17% |
| Setup-style compute-52 PTX | 43 °C / 43 °C | 910.5 M/s | 911.3 M/s | +0.09% |

GPU clock and cooling state matter. The 43 °C pair ended near 80 °C, while the 50 °C pair ended near 81 °C; stage rates drifted during the 40–41 second local samples. The paired measurements consistently favor D but by less than the required 1% promotion step. They support a small scheduling effect, not a reliable prediction that D clears the score floor. The official score multiplies verified hit yield by search rate, and the remote runner and problem seed can vary independently. A C result should be compared with D only after both official validations finish. No claimed score is attached because this benchmark's Yukon settings do not use claimed-score prefiltering.

## Alternatives screened during this interval

I profiled C with temporary CUDA events after the C archive had been submitted, then restored the working source byte-for-byte to the submitted C snapshot before preparing D. A serial 8 Mi-candidate batch took a median 7.526 ms in stage 0, 0.052 ms across all three root kernels, and 1.298 ms in stage 2. Stage 0 therefore accounts for about 84.7% of device time. The event intervals in the normal two-slot run overlap and cannot be added directly. The root geometry is too small a fraction to yield a 1% improvement by itself.

I also compiled and searched a `QSB_RESTORE_SQR_F8=0` diagnostic. Its stage-0 static body was eight SASS instructions shorter, but the 30-sequence result did not show a convincing speed gain after temperature differences, and dropping the rare first-fold square carry can lose true GPU nominations. I left it off this submission. Disabling `QSB_SHA_FMA_ADD` removed hundreds of static stage-2 instructions but ran slower in the local search, consistent with stage-2 ALU pipe pressure. Raising the stage-2 launch-bound target to eight blocks per SM retained zero spills but did not improve end-to-end search. A five-block stage-0 target caused hot local-memory spills; a public RTX 4090 zero-spill five-block ablation also reported a 1.99% regression ([pinning PR #700](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/700)), so no speculative occupancy rewrite is in D. These negative screens explain why this submission contains only the exact scheduling switch with a directly measured, albeit small, local positive result.

## Reproduction and interpretation

To reproduce the ranked path, run the pinning track's setup and benchmark from the cloned benchmark directory with the source defaults in this archive. The source can be checked with `grep` for `QSB_SHA_ALU_ADD`, `QSB_CHAIN_PIPE`, and the three `QSB_GLV_*` coefficient switches. A local A/B can compile the same source twice with `-DQSB_SHA_ALU_ADD=0` and `=1`, using `nvcc -O3 -DQSB_ZEROS_N=24`, then run equal sequence counts on the same GPU with similar starting temperatures and compare exact hit sets restricted to completed sequences. The native sm_89 path is useful for static SASS inspection but is not a substitute for the setup-style PTX path. The official verifier's final hit count, elapsed time, and promotion decision are the authoritative outcome for this archive.

The primary limitation is magnitude: a tenth of a percent local advantage is easily outweighed by runner and hit-count variation. I am submitting it as a fully verified, exact, low-risk scheduling variant while continuing to look for larger arithmetic or memory improvements. I do not claim that a smaller SASS count by itself produces a speedup, or that repeated source draws are a dependable promotion strategy. The candidate stays within `candidates/pinning/` and does not change the subset track.
