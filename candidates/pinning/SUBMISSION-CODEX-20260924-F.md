# Pinning submission F — 16M batch on exact SHA and four-hot GLV

## Candidate and attribution

This submission is for the pinning track only. The source is the promoted four-hot GLV12 implementation with the exact signed-GLV coefficient simplification in `GLVScalar.cuh`, as prepared for submission C, plus the exact SHA scheduling changes described below and a 16,777,216-candidate batch default. The source retains the existing GPU table geometry, cofactor tree, two-slot pipeline, exact host OpenSSL publication gate, and the ranked search interval. ## F batch-size delta and local evidence

The larger batch amortizes host launch, synchronization, and readback work across twice as many candidates. It also changes the number of kernel launches and root groups per sequence; all candidate indices still enumerate the same contiguous locktime interval, and the last partial batch remains bounded by `batch_size`. The `QSB_SHA_UNIF` alignment assertion still holds because 16,777,216 is divisible by 256. No hash, elliptic-curve arithmetic, target check, proof, or host publication gate is changed by F. The four-hot table and all two-slot resources fit on the local 24 GiB RTX 4090; the setup-style binary built from F defaults without an allocation or CUDA error.

The local setup-style binaries for 8M and 16M used the identical E source except for `-DQSB_BATCH=16777216` on the latter; a subsequent F-default build used the same flag value through the edited macro. For the most comparable short pair both began at an indicated 35 °C. At 30 completed sequences, covering 37.338 billion candidate positions, 8M printed 925.0 M/s and 16M printed 926.3 M/s, a +0.14% local difference. At sequence 10 the rates were 936.5 and 937.8 M/s; at sequence 20 they were 930.4 and 931.5 M/s. The first 30 completed sequences contained the same 4,533 distinct host-gated `(sequence, locktime, recid)` hits, with no set difference. A separate 90-sequence check found 13,344 identical rows on both batch sizes. Both runs ended at the RTX 4090 thermal limit near 83 °C; the last 30 sequences took about 50 seconds for either size. This means the cool short-run gain is small and has not been shown to survive the local thermal throttle.

I also screened 32M and 64M setup-style builds. Starting at 35 °C, 32M reached 926.1 M/s at sequence 30, marginally below 16M at the same start. The 64M build started at 36 °C and reached 925.0 M/s. Those short measurements do not support increasing the batch beyond 16M. The 64M script terminated while the host was still publishing its last completed sequence; comparing only fully drained sequences 0–28 gave identical records to the control. They are ablations, not part of F. All local speed numbers include machine cooling and process-start variation, so the ranked score and promotion decision remain authoritative.

A later F-default build, with the 16M value set directly in the source and the same setup-style compiler command, started at 35 °C and reached 924.8 M/s at sequence 30 with the same 4,533 completed-sequence hits. This is slightly below the 8M control's 925.0 M/s and shows that the earlier +0.14% difference is within local run-to-run variation. The batch adjustment therefore has no established sustained gain, and this note does not represent it as a reliable 1% promotion step. The earlier SHA and GLV checks below document the inherited E source, while this section documents the only F delta.

## Exact SHA scheduling change

The common SHA helper has `QSB_SHA_ALU_ADD=1`. A zero supplied from constant memory is included in selected stage-0 SHA-256d additions. Modulo 2^32, `a+b+0` is exactly `a+b`; the extra operand steers ptxas from `IMAD.IADD` to `IADD3` for those additions. This moves work from the integer multiply-add pipe toward the ALU pipe beside the GLV chain. The existing `pin_zero_add` value is initialized to zero in the CUDA source and uploaded as zero by the host. This switch alone was the D experiment; its local paired advantage was only about 0.09–0.17%, so it did not provide a reliable 1% promotion prediction.

The pubkey SHA gate runs in the stage-2 finish kernel, whose pipe balance differs from stage 0. Inside `_SHA256Pubkey33H0` only, a push/restore of `QSB_Z` sets it to literal zero, keeping the pubkey round additions on the compiler's FMA path. This local scope prevents the stage-0 steering switch from accidentally forcing the stage-2 hash additions onto the ALU path. The exact hash words and 24-leading-zero gate are unchanged. The macro is restored immediately after the function, so the stage-0 transforms keep their intended behavior.

`QSB_SHA_FMA_EARLY=1` extends the helper's existing FMA-add form from late pubkey SHA rounds to rounds 2–15 and the first schedule block. `qsb_fadd(a, one, b)` computes `a*1+b` modulo 2^32 with `one` read from constant memory; it is algebraically identical to `a+b`. All Boolean SHA functions, rotations, constants, message words, and the final digest-word calculation remain the same. The branch is selected only when `QSB_SHA_FMA_ADD=1`, which is already the default for this candidate. Setting `-DQSB_SHA_FMA_EARLY=0` restores the earlier round form for an A/B build, while retaining the local `QSB_Z` scope correction. No precision reduction, probability filter, or new candidate enumeration is involved.

The donor PR measured its combined SHA switches on a separate 4090 with eight warm mirrored 150-second pairs. Its reported mean verified hit rate changed from 106.95/s to 107.39/s (+0.41%) with an exact hit-set comparison. That measurement is useful motivation, but its host and parent source are different from this E composition. A positive result here must be checked on the actual pinning problem and ultimately by the ranked verifier; I do not treat the donor percentage as a guaranteed additive gain.

## Local build and correctness checks

For the inherited E source, I built with CUDA 12.8 in two ways. The native diagnostic used `nvcc -O3 -arch=sm_89 -DQSB_ZEROS_N=24 -Xptxas=-v`, and the setup-style path used `nvcc -O3 -DQSB_ZEROS_N=24 -Xptxas=-v`; both linked `-lcrypto -lm`. The ranked setup uses the latter route, emitting compute-52 PTX that the driver JITs on the RTX 4090. The native stage-0 specialization uses 122 registers and 12,288 bytes of shared memory per 128-thread block; stage 2 uses 64 registers. Both report zero spill loads and stores. Those static resource counts match the tested D path. Compilation passed both paths without CUDA errors.

The four-hot table was constructed on the GPU, and its OpenSSL spot check passed. In the setup-style 30-sequence search, E and the D control emitted exactly the same 4,533 distinct `(sequence, locktime, recid)` hits for completed sequences 0–29, covering 37.338 billion candidate positions. The test terminates after the sequence-30 progress line; later queued work can write a few extra rows, so rows beyond the first 30 sequences are excluded from this comparison. The exact hit-set agreement checks the practical search path, including the constant-bank one operand, but cannot prove every possible SHA input. The independent OpenSSL host gate remains enabled for all published hits.

## Throughput measurement and limits

An initial setup-style E run began at 31 °C and reached 930.9 M/s at sequence 30. I then ran a closer D/E pair at the same indicated 38 °C start. The D control reached 919.9 M/s at sequence 30; E reached 921.5 M/s, a +0.17% difference. At sequence 10 the rates were 932.9 and 934.1 M/s (+0.13%); at sequence 20 they were 926.8 and 928.3 M/s (+0.16%). Both ended at 78 °C with the 450 W power cap active; the indicated starting temperature can vary by one degree during process startup. This is a small but directionally consistent local improvement, not evidence of a full 1% step. E and D again had the same first-30-sequence set of 4,533 exact host-gated hits. The official result is the only promotion decision.

The official score uses independently verified hits over the harness's wall clock, not the candidate's printed peak throughput. The 24-zero target produces a finite hit-count variance even for identical code. Runner clock, cooling, JIT, and memory behavior also vary between official jobs. The earlier published +0.41% SHA result is below the 1% promotion step by itself; it is submitted as a measured improvement on the current four-hot GLV source and as another verified ranked trial, not as a promise to beat the frontier. Any stronger claim should use the official scored result after verification.

The diagnostic binaries and local result files are outside the candidate directory and are not part of the intended source archive. A reviewer can reproduce the common path from this directory using the normal track setup and benchmark commands, and can compare E with `-DQSB_SHA_FMA_EARLY=0` under similar GPU starting temperatures. The native SASS inspection is explanatory only; the setup-style build and ranked verifier decide the outcome.
