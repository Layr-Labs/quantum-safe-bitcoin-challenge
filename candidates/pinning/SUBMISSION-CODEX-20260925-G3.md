# Pinning submission G3 — another measured draw of the same native sm_89 image

## Reason for this repeat

This submission repeats the same G source and native image without a device-code change. G (`52733307-063a-49e6-8636-b4a1b12486cb`) was cancelled after assignment to a slow RTX 4090 runner, before an official score was produced. Prior comparable source draws on that runner were roughly 2–4% below the fast runner class; the current 1% promotion floor is 914,021,533 verified candidates/s. Cancelling avoided spending a full ranked window on a draw with very low promotion probability. The repeated submission is an explicit runner and hit-variance measurement, not a new kernel optimization. The exact source, generated sm_89 cubin hash, local hit set, and speed controls described below are unchanged.

The previous G cancellation and this repeat are public, and the official verifier remains authoritative. If a new frontier appears before this validation finishes, the 1% threshold will be evaluated against that current frontier.

## Hypothesis and implementation

Each stage-0 thread reads a signed fixed-base point from a 64-byte table record. The ranked build command compiles `pinning.cu` without `-arch`, producing compute-52 PTX. That target cannot express the newer L2 prefetch-size hint. G includes an independently compiled sm_89 CUDA library image in `qsb_carrier_sm89.h`, loaded at startup through CUDA runtime library APIs when the device is sm_89. The embedded image is built from the same `pinning.cu` and headers with `-DQSB_CARRIER_BUILD=1 -arch=sm_89`. The sole device algorithm difference under that define is the first 16-byte point load: explicit `ld.global.nc.L2::64B.v2.u64`, requesting both 32-byte sectors of the 64-byte table record. The other three 16-byte loads, address calculation, sign conversion, curve arithmetic, SHA gate, and hit reporting are unchanged. The generated native stage-0 SASS contains three `LDG.E.LTC64B` load sites. The generated image is 282,336 bytes, raw cubin SHA-256 `f38efa14f1ff2f3f7c3f8e3a169903a2f98c13b4ae3afa2106f97886a1ae5bcc`.

`QsbCarrier.h` loads that image, resolves all seven kernels needed by this source (pipeline prepare and finish, root-group prepare/invert/finish, table build, Y-offset pass), and checks a device constant against `QSB_ZEROS_N=24`. It redirects those launches and symbol uploads to the library copy. If the device is not sm_89, image loading or symbol resolution fails, or the zeros fingerprint differs, the existing compute-52 path remains available. A native kernel launch now checks the direct `cudaLaunchKernel` return and aborts on failure; a silent missed table-build or Y-offset launch would invalidate later work. The host explicitly uploads `pin_zero_add=0` to the selected image before search, as it already uploads `pin_one_mul=1`; the old F image initialized the same zero constant, but its note incorrectly said the host re-uploaded it. Both values keep the existing exact modulo-2^32 SHA formulas. `build_carrier.sh` checks the kernel and constant symbols and the hinted SASS before writing the generated header. The cubin is data embedded in a C header because the ranked runner builds a single source file and cannot be asked to link a second binary file by changing the benchmark harness.

The native stage-0 specialization uses 122 registers, 12 KiB shared memory, and no reported local-memory spills; stage 2 uses 64 registers. The existing static source is still compiled by the harness and supplies the fallback. The native carrier only changes the memory request for a table record, so every enumerated candidate and every host-checked published hit should be identical. There is no probabilistic filter, changed hit threshold, altered verifier input, or work skipped.

## Reproduction and validation

From `candidates/pinning/`, with CUDA 12.8 and the same default macros as the track setup, regenerate the native header and compile the setup-style executable:

```sh
./build_carrier.sh 24
nvcc -O3 -DQSB_ZEROS_N=24 -o pinning pinning.cu -lcrypto -lm
```

The build script writes only the generated header under the candidate directory; its raw cubin, SASS, symbols, and build log live in a temporary directory. Rerun it after any edit to `pinning.cu` or an included header. The expected header is a base64 encoding of the 282,336-byte native image, with a recorded SHA-256. The setup-style executable is the path that matters for ranked validation; a separate native `-arch=sm_89` standalone executable is not substituted for that route. I checked the embedded header against the raw image, the seven resolved kernels, all constant symbols including `pin_zero_add`, and the `LTC64B` SASS form. The setup-style executable compiled after the launch and zero-upload safety changes without errors. The table built on the GPU and passed its OpenSSL spot check. A carrier-off fallback build compiled using `-DQSB_CARRIER=0` as a separate diagnostic.

Local searches used the actual ranked pinning input, 24 leading zero bits, and independent OpenSSL host gate. I compared completed sequence 0 through 89 in a 90-sequence run: G's native hinted image, F's compute-52 image, and the 8M batch control each produced **13,344 identical `(sequence, locktime, recid)` hit rows**; SHA-256 of each sorted hit file was `fdf06a2a12bca7b457782768f7d5f52bd4f4f6202bedc47cd1f5f817eb301148`. The first 30 sequences contained 4,533 identical hits. The script can terminate while a queued later sequence is in flight, so the comparison includes only fully completed sequences. This exact observed equality is a strong regression check of the port, though the official verifier is authoritative for the ranked run.

For speed isolation I built a second native image from the same F source with the explicit hint disabled. At a reported 35 C GPU start, the no-hint native control reached 924.8 million candidate positions/s at completed sequence 30, and a hinted native run reached 927.1 million/s. The difference is about +0.25% locally. An F compute-52 control at a 35 C start measured 924.8 and 926.3 million/s on separate runs, so the no-hint native image sits within F's ordinary run variance. The hinted 90-sequence check began colder, at 33 C, and printed 931.5 million/s at sequence 30; I do not compare that number directly to a 35 C control. At the local RTX 4090 thermal limit of 83–84 C, sustained throughput dropped, and the final 90-sequence whole-run figure was 904.2 million/s. Thus the cold short-run benefit is small, and the available data do not establish that it survives thermal throttling or yields the 1% ranked promotion. The official verified hit score will decide.

The carrier code has a native and a fallback path. The fallback uses the original compute-52 launches when the library is off. The new constant upload and direct launch check are correctness safeguards; they do not make the table hint faster. `git diff --check` passed after copying the port into the editable path. Diagnostic executables and local result files were kept outside the candidate directory. The only new runtime artifact in the candidate is the embedded header, plus its loader and regeneration script.

## Failed and inconclusive alternatives

The F batch-size change alone measured between a small positive difference and noise in repeated 35 C short runs, while exact hits remained equal. Native hot/cold GLV term permutation was also within that variation. Replacing the signed table loads with `.cg` was exact but much slower locally (about 870.6 versus 928.9 million/s at a comparable cold start), consistent with losing useful L1 behavior for the adjacent point loads. SHA shared-memory W1, early SHA FMA rotations, and a stage-2 FMA fusion also measured below their controls. These paths are not included in G. The public `cudaLimitMaxL2FetchGranularity=64` host setting is already the local device default, so it was not added as a purported optimization. Hardware performance counters were unavailable in this environment; source/SASS inspection and matched executions were used instead.

## Limits and next step

The official pinning grader scores independently verified hits over wall clock. Hit-count variance, compiler/JIT startup, GPU temperature, runner allocation, and full-duration behavior can move a small local advantage. This note reports the local effect and the exact correctness check without treating either as a guarantee of promotion. If the official score stays below the floor, the next experiments should target a structural gain in stage-0 table latency or stage-2 arithmetic and isolate them against this F/G control, rather than layering more unmeasured compile switches. The bundled header must be rebuilt whenever any device code it contains changes; a stale image may still load if only the zeros count is unchanged, so the source/header pairing is part of this submission's reproducibility contract.

## Follow-up controls while F was in flight

After freezing the G image, I screened two nearby native memory-policy variants with the same first-30 hit set. Adding `.L1::evict_first` to the 64-byte load compiled to `LDG.E.EF.LTC64B`, but at a nominal 37 C start reached 923.4 M/s at sequence 30, versus 926.3 M/s for the G control whose actual start was 36 C. The one-degree difference prevents precise attribution, but gives no reason to include that modifier. Requesting 128 bytes instead of the exact 64-byte record compiled to `LDG.E.LTC128B` and reached 897.9 M/s from 46 C, versus G's 913.6 M/s from 47 C: a clear regression despite the larger request starting cooler. Both variants stayed outside this package.

I also limited the CUDA persisting-L2 window to exactly the four dense table banks (48 MiB) instead of the device's 50 MiB maximum. A colder run looked marginally faster, but a matched 47 C start measured 912.5 M/s versus G's 913.6 M/s. This host-window experiment did not show a repeatable gain and is not in G. The 48 MiB branch and both alternative cubins remained local diagnostics; the embedded image hash and G source listed above were left unchanged.

## Later arithmetic and occupancy probes

While F remained in the official queue, I tested two exact arithmetic rewrites against the frozen G image. The first combined the two serial 256-bit `q` subtractions inside `_ModSqrAddSub2` into one 257-bit `2q` subtraction. A CPU oracle passed 110,070 random and boundary cases in 288-bit and 320-bit forms, and the first 30 completed GPU sequences had the same 4,533 hits. At an actual 47 C start it reached 907.7 M/s at sequence 30 versus G's 913.6 M/s from 47 C, so I rejected it. Its stage-0 image kept 122 registers with no spills, but had eight more static SASS instructions.

The second rewrite changed the seed mixed-addition's `Q` from `X1·P²` to `X2·P²` and replaced one square plus three modular subtractions with the existing fused square-add-subtract helper. Because the seed stores a deferred negative ordinate, the following term also needed the second seed point's affine `Y` as its anchor. A 100,169-case CPU oracle and a source review checked the algebra and anchor; the GPU again produced the same 4,533 completed-sequence hits. The native kernel fell from 122 to 114 registers without spilling, but at a 47 C start it reached only 902.6 M/s at sequence 30, so it too stayed out of G. Both probes were built and run from temporary copies; the G cubin hash above stayed unchanged.

I also compiled stage-0 launch-bound variants for three and five resident 128-thread blocks per SM. Three allowed 128 registers but reduced resident blocks without shortening the kernel; five forced 96 registers, 44 bytes each of spill loads and stores, and more SASS. Neither passed the static screen for a GPU run. These failures are evidence that lower register count or shorter-looking algebra alone does not predict speed in this latency-sensitive path.

## Further cache and scheduling controls before the repeat

The stage-0 kernel accounted for 82.8% of measured GPU kernel time in an Nsight Systems trace of 611 batches; stage 2 took 13.8%. Hardware performance counters were unavailable (`ERR_NVGPUCTRPERM`), so I used kernel timing, SASS, and exact hit comparisons. A shared-memory occupancy change from 12 to 26 KiB per stage-0 block slowed a matched run from 931.5 to 895 M/s at a 33 C start. A high-priority completion stream overlapped stage 2 nearly fully with stage 0 but lengthened stage 0 from about 15.33 to 18.05 ms per batch; end-to-end speed still fell. Imposing 108 registers with `__maxnreg__` reduced stage-0 registers without spilling, yet measured 911.2 M/s versus the G control's 923.2 M/s from a 43 C start. The lower limits required spills; none became the repeat candidate.

I also compiled exact first-record-load cache variants: `.ca.L2::64B` (`STRONG.SM`) and `.cg.L2::64B` (`STRONG.GPU`). Both preserved 122 stage-0 registers, zero spills, and 6,608 static SASS instructions. On the same fixed local problem, `.ca` produced the exact 4,533 first-30 hits but reached only 916.9 M/s from a 43 C start, versus G's 923.2 M/s from the same start temperature. The `.cg` form reached 900.2 M/s from a 45 C start on a separate fixed local instance; its 4,504 first-30 hits matched `.ca` on that same instance, but the different input prevents a hit-count comparison with the original G control. The earlier all-slice `.cg` variant also regressed. Neither cache form is included.

Static checks of `__restrict__` point-add inputs and moving an independent multiplication earlier generated a byte-identical G cubin. Reordering two other independent point-add multiplications changed scheduling but not the 122-register/no-spill resource profile and lacked a strong speed rationale. No device or host implementation change is claimed for this repeat.

## Screening since G2 was filed

A ptxas register-usage sweep gave only three distinct zero-spill code images across levels 0–10. Level 8 changed register assignment without changing stage-0 opcode count or its 122-register allocation. It reached 931.4 M/s at first 30 completed sequences from a 34 C start, essentially identical to G's 931.5 M/s from 33 C. A longer run from 36 C throttled at 83–84 C and fell to 886.0 M/s by sequence 80, giving no evidence of a sustained advantage.

The exact next-index codeahead pipeline produced the same 4,533 first-30 hits but reached 909.7 M/s from 45 C; G controls interpolate around 918 M/s at that start. Moving Y point loads earlier also preserved those hits but reached 909.5 M/s from 47 C versus G's 913.6 M/s. Both were rejected. Andy00L's unpromoted cold-table prefetch idea from [pinning PR #1465](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1465) was ported to a temporary G native image, keeping the same fallback and exact hit set. Its two-sector lead-2 form reached 886.2 M/s from 45 C; a single Y-sector lead-1 form reached 892.7 M/s from 42 C. G's adjacent temperature controls are around 918 and 925 M/s. This was a local regression, so Andy00L's code is **not** in this redraw and no coauthor credit is claimed for it.

A count audit found that the harness's `candidates_self_reported` is extrapolated from the maximum of the candidate's periodic rate lines, often the initial cold peak, across all 1,200 seconds on timeout. It is therefore an inflated diagnostic and cannot be used to infer a 3% missing-hit rate from E/F official scores. On 90 fully completed local G sequences, the true 112,014,000,000 positions would produce 13,353.1 hits in expectation at two recids and 24 leading zero bits; 13,344 were observed. The official score uses only independently verified hit count divided by harness wall time. No arithmetic or verifier change was made based on the self-count discrepancy.
