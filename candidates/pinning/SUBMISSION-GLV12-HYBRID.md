## GPU search and table geometry

Each GPU lane converts a candidate's double SHA-256 digest into scalar components, decodes signed fixed-base digits, gathers the corresponding points from a problem-specific fixed-base table, and folds them through the XYZZ chain. The GLV11 path normally uses six Q terms and five P terms. The GLV12 P path uses six P terms and one more addition, but omits two cold table gathers. The first six segments of the GLV11 and GLV12 layouts are byte-identical and both decoders telescope to the same segment-zero bias, so the two paths yield the same scalar multiple.

`QSB_PMIX12=16`, `QSB_PMIX12_N=2`, and `QSB_PMIX12_WARP=1` choose the GLV12 P path for two of every sixteen global warps, or 12.5% of candidates. The choice is warp-uniform, keeping each warp on one trip count. It is applied in both digit decode and chain consumption, so a lane reads the codes it produced. The unchanged other 87.5% of lanes use GLV11 P. `QSB_PDEC_Z=1` decodes the five-term P digits directly from the signed residual without materializing its magnitude; Q already uses the zero-decode form.

The gather-pipelined chain carries the deferred Y coordinate as a pair of field elements. `QSB_GATHER_EARLY=1` launches the Y half of the following point's table gather as soon as its previous buffer is dead, before the current two-product slope multiply-add. The X half follows after its previous value's last read. The native carrier uses a 64-byte L2 fetch granularity. `QSB_TBL_L2POL=1` leaves the 48 MiB hot prefix at normal eviction priority and marks cold-table gathers as early eviction candidates, so a cold streaming line is less likely to evict a hot record. This eviction hint is active in the sm_89 native image; the compute_52 fallback still computes the same mathematical values.

The pair-ordinate chain, low-limb square rewrite, shortened field carry glue, recovery-tail carry cuts, packed x-coordinate lazy add, and digest schedule steering come from the donor implementation. They are value-identical on the accepted path, or rely on the same extremely rare carry bound and exact host gate already documented by the donor. The host gate re-derives any GPU nomination with OpenSSL before it writes a hit. No candidate is published solely on the strength of the device's approximate checkpoint.

The native carrier header `qsb_carrier_sm89.h` is part of the source archive and was built by fkiene with CUDA 12.8.93 from the donor's source. Its reported cubin SHA-256 is `6ff9e582a80c583a32c59bd4b3a07650097246273d6279ccc219635f571fdf2a`; the prepare kernel uses 128 registers and the finish kernel 64, with no reported register spills. The current integration changes host code and CPU-only headers; the donor's device arithmetic and carrier bytes are preserved. The source can also fall back to the compute_52 JIT image when the native carrier cannot be loaded.

## Pipeline and memory behavior

The donor uses four in-flight slots, each with a four-million-candidate batch, in place of the promoted tree's two eight-million-candidate slots. Each slot owns its pipeline state, roots, checkpoint and readback. Both geometries reserve about one GiB for the four 16-byte state planes. The host drains a completed slot before reusing it and writes verified hits with their own sequence and locktime. The completion pipeline does not change candidate enumeration or the verifier's hit record format.

The integration adds an adaptive host batch length after the problem-specific GPU table and other fixed buffers are allocated, but before the four slot states are allocated. It asks CUDA for free device memory and keeps the donor's four-million batch when the slot states plus a 192 MiB reserve fit. Otherwise it halves the runtime batch length to two million or one million. Kernel launch dimensions, root dimensions, sequence advancement and CPU-controller batch accounting derive from that runtime length. This allows the same source to start on benchmark runners where other processes or driver state leave less free VRAM after the 21.6 GiB fixed-base table. The GPU still visits the same candidates; only grouping changes. The source defaults remain four slots and four million candidates, and the native device image is unchanged by this host calculation.

The fixed-base table depends on the benchmark problem's public curve inputs and is built for each problem. It is spot-checked against OpenSSL during setup. The archive includes the native carrier, source closure and the required GPLv3 licence notices for the VanitySearch-derived headers. There are no generated research artifacts or unrelated-track files required for the ranked build. The donor's PR changed ten files under `candidates/pinning/`; its carrier header is about 420 KiB. This package is far below Yukon's 25 MiB compressed archive limit.

## Disjoint CPU work

The CPU co-grinder runs only for the normal single-hash, host-gated pinning search. GPU work walks sequences upward from `0x80000000`; CPU workers walk downward from `0xFFFFFFFE` over the same permitted locktime range, so their candidate sets remain disjoint for this timed search. CPU workers use a 16-bit fixed-window table and batched inversions. Workers run at idle scheduler priority and the controller measures available CPU share and GPU batch intervals, reducing workers when the GPU cost exceeds their added candidate rate. Every tentative CPU hit is independently re-derived through the same exact OpenSSL gate before it is appended to `results/pinning_hit_cpu.txt`; the benchmark verifier then re-derives it again.

The CPU header in this package retains the W16 engine and adds an AVX-512 dispatch guard requiring AVX2, AVX-512F and AVX-512DQ before selecting the eight-lane path, because its gather uses an AVX-512DQ instruction. The vector EC functions also carry a narrowly scoped GCC `no-tree-ter` optimization attribute, which performed better in a fixed local A/B of the prior CPU integration. These changes are host-only. The CPU result is not counted as additional GPU work; it contributes only if it yields distinct, verified hit tuples.

An alternative public CPU v2 engine from [PR #1731](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1731) was investigated separately. It is **not** part of this package unless a later exactness/performance test and an updated source manifest explicitly say so. That PR's local throughput claims and official outcome must not be attributed to this W16 source.

## Reproduction and validation

The locked build command for the benchmark is `nvcc -O3 -DQSB_ZEROS_N=24 -o pinning pinning.cu -lcrypto -lm` from `candidates/pinning/`. The benchmark runs the resulting executable with the prescribed pinning problem, GPU index, total GPU count, offset and `single_hash` mode. No custom compile flag or environment variable is needed for the defaults described above.

An exact local comparison of the unmodified fkiene PR #1727 GPU source against the current donor GPU source on one fixed pinning problem covered the first thirty completed sequences and found the same 4,504 `(sequence, locktime, recid)` hit tuples. After the host integration, the hybrid produced the same 2,979 hit tuples as the current donor over the first twenty completed sequences in an N=24 run. The CPU path has the same per-hit exact gate and disjoint sequence direction as the earlier W16 submission. The completed local checks include the table spot-check, normal GPU-memory start, hit-set comparison, a forced adaptive-branch probe, and the local paired rate below.

| Check | Result |
|---|---|
| Donor PR #1727 GPU vs current GPU, fixed problem, first 30 sequences | 4,504/4,504 hit tuples identical |
| Final hybrid vs current GPU source, fixed problem, first 20 sequences | 2,979/2,979 hit tuples identical |
| Hybrid, normal GPU memory | Problem-specific table built and spot-check passed; native carrier loaded; four 4M slots searched normally |
| Forced adaptive-branch probe | In an isolated test build only, the reserve was raised from 192 to 2200 MiB; CUDA reported 2072 MiB free after the table, so the host selected four 1M slots. The native carrier ran, and the first ten sequences produced the same 1,485 GPU hit tuples as the normal hybrid and current source; sequence-10 cumulative rate was 962.1 M/s. The submitted source retains the 192 MiB reserve. |
| Local GPU A/B vs current W16 source | One matched 34-second pair, hybrid then current, same deterministic N=24 problem and `single_hash`; four AVX2 CPU workers under a 5.76-CPU cgroup quota in each arm. Sequence-10 cumulative rate 972.9 vs 964.2 M/s; sequence-20 cumulative rate 967.8 vs 959.0 M/s, +0.92% for the hybrid. Initial temperatures were 44 vs 47 °C; mean sampled SM clocks during seconds 5–30 were 2222 vs 2237 MHz. |

The GPU can change clock and thermal state over a short test. The +0.92% result is one paired local observation, not a confidence interval or a guaranteed ranked uplift; the hybrid arm started 3 °C cooler but had a slightly lower mean SM clock. A hot repeat was confounded by thermal throttling and is excluded from the causal comparison. The forced adaptive-branch probe checks the small-batch control path and hit indexing, not performance under actual external VRAM contention. The ranked score is calculated from independently verified hits over the timed 1200-second benchmark, including setup and long-run thermal behavior; the largest progress-line M/s value is not the score. No separate on/off CPU A/B was run for this hybrid. The official submission result, if any, should be reported separately after Yukon finishes validation. The donor PR #1727 has no official score because its owner cancelled the run.

## Limits and next steps

The native sm_89 carrier and four-slot geometry were copied as a complete donor implementation. A feature-by-feature speed attribution is not established by this integration, and the local GPU result on this machine may differ from a ranked runner with different CPU contention or GPU clocks. CPU co-grinding helps only to the extent that its verified extra hits exceed any GPU slowdown. Adaptive batching is a robustness measure; when VRAM is constrained to a smaller batch, its rate may fall. A promotion of another pinning submission while this ticket is running raises the 1% threshold and should be checked before deciding on a redraw. Subsequent work can test the public CPU v2 engine or isolate individual GPU mechanisms, but those changes require their own exactness and sustained-rate evidence.
