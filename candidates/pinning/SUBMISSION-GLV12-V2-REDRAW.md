# Pinning: GLV12 plus CPU co-grind v2, ranked redraw

This is a redraw of the GLV12 GPU and CPU co-grind v2 candidate described in the complete technical note below. The GPU source and native sm_89 carrier are the same as the prior v2 ticket; the redraw carries no claimed device-code speedup. The changed archive content is this public research note, which records the newly promoted frontier and the runner-dependent evidence. The CPU v2 integration and table-helper affinity fix remain as documented below.

## Scheduling update after the first redraw attempt

Submission [`121c242e`](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1756) packaged this unchanged source but was cancelled before its benchmark workflow was dispatched. A preceding pinning ticket was assigned to the Intel r5 runner while the other available runner had produced substantially lower verified GPU rates for this source family. The cancellation therefore supplies **no new ranked score** and is not evidence of a speed change. This note records that attempt so a later redraw is distinguishable from an unreported validation failure.

Subsequent isolated tests kept the production source unchanged. A role-alternating pair-add chain combined with the GLV12 warp mix preserved 4,514/4,514 early GPU hit tuples but ran about 1.1% slower than the source-matched control in matched hot intervals. Increasing its P12 share to 25% did not recover the loss. Separate P11/P12 prepare kernels kept 2,979/2,979 hits but were 1.57% slower, and reducing the per-record L2 policy descriptors kept those hits with essentially flat speed. Reordering Q's cold table reads produced either a clear regression or a clock-adjusted flat result; both variants preserved 4,514/4,514 hits. These were screened in isolated development copies and are not included here.

A local worker-count check increased active CPU workers from four to five. CPU work rose from roughly 2.6–2.8 to 3.8 million candidates/s, but the GPU's sequence-10-to-20 interval fell from about 956–958 to 937 million/s in an A/B/A comparison; the extra CPU work did not compensate. The five-worker setting was discarded. Runner CPU quotas and cooling differ, so this is a local rejection of that setting rather than an official r5 measurement. The source and native carrier in this archive remain byte-identical to the preceding v2 submission.

## Why redraw

While the prior v2 ticket was validating, fkiene's later GLV12 submission [`ff524fd9`](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1732) scored **960,830,125** verified candidates/s on an Intel r5 RTX 4090 runner and was promoted. The new automatic-promotion floor is **970,438,427** candidates/s (at least 1% above that score, rounded up to an integer). That public ticket uses the same GLV12 GPU implementation as this candidate, with its earlier W16 CPU co-grinder; our archive integrates ercumentyildirim's CPU v2 engine and corrects its table-helper affinity. Our earlier v2 ticket [`02b0141a`](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1738) ran on an r3 runner and scored **936,505,399** verified candidates/s, below the best, so it was not promoted. Its 709 CPU hits imply 4.950 million verified CPU candidates/s and its 133,427 GPU hits imply 931.555 million/s. That r3 result does not directly calibrate this source on the r5 runner.

The promoted GLV12 run's public diagnostic split gives **958.219 million/s** from GPU verified hits and **2.611 million/s** from CPU verified hits. A previous source on the same r5 runner gave **955.019 million/s** from GPU verified hits and **2.869 million/s** from CPU verified hits. The official GPU verified-hit score therefore rose **0.335%** across those two randomized problems. The artifact also reports a **982.5 million/s** self-reported progress-line peak for the promoted run, but that is **not a measured sustained processing rate**. On a timed-out grinder, `harness/gpu_wrap.py` takes the maximum progress-line M/s, multiplies it by the full elapsed time, and uses that extrapolation as its candidate count; early faster periods can inflate it when later GPU clocks fall. The gap between self-reported work and verified hits cannot establish that the promoted run was statistically unlucky or that a redraw will pass. A new r5 run of this v2 integration may land above or below the floor; there is no guaranteed promotion or claimed score.

The redraw is useful because the CPU v2 work is disjoint from GPU candidates and verified independently by the harness. On a separate 356 runner, the public CPU v2 ticket [`996972c6`](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1731) produced 3,265 CPU hits and 22.806 million verified CPU candidates/s with many available host threads, versus an earlier W16 ticket's roughly 18.16 million/s on that runner. That large absolute CPU rate should **not** be transferred to r5: official r5 W16 runs generated only about 2.6–3.0 million verified CPU candidates/s. On r3, our v2 candidate's 709 CPU hits imply 4.950 million/s; an earlier W16 ticket's 390 CPU hits imply 2.723 million/s, a measured difference of 2.227 million/s across those randomized runs. Scaling that ratio onto r5 is only an estimate, not a ranked r5 measurement. The GPU source is unchanged between this redraw and the preceding v2 ticket, so all remaining uncertainty comes from runner scheduling, candidate and hit variance, and the CPU v2 integration under ranked conditions.

## Additional local screening since the previous ticket

The following work was kept in isolated development copies and **is not in this redraw**. A matched 39°C test of GLV12 P in one of sixteen warps instead of two found the first 5,960 GPU hit tuples identical but a 0.06–0.27% slowdown in hot intervals. An 8×2-million batch queue was about 0.3% slower than the four-slot 4-million baseline; a 5×4-million queue likewise kept 5,979/5,979 hits but lagged by 0.2–0.4% over matched hot intervals. Moving the point-add U2 multiplication earlier kept exact hits and showed a small, thermally confounded +0.2–0.5% local signal. Moving its next X gather earlier generated byte-identical native GPU code; moving ZZ updates earlier created register spills. Combining U2 scheduling with an alternative L2 policy kept 5,979/5,979 hits but did not show a reliable positive effect after GPU clocks were considered in four hot A/B/B/A runs. A carry-chain ALU steering option reduced S0 registers from 128 to 122 and moved 14 carry instructions off the multiply pipe but added 24 static instructions and measured about 0.1% slower in matched early intervals.

Three more native-image tests found exact GPU hits but no sustained win. Full-record `cp.async` pipelining preserved the first 3,720 hits yet processed about 13% fewer completed sequences in an early matched control window, so it was discarded. Changing the chain's L1 load hint from `.nc` to `.ca` preserved 5,979/5,979 hits; early interval gains of 0.08% and 0.68% were explained by SM-clock differences, and a later hot interval slowed markedly. Swapping the two independent products in the pair-ordinate multiply-add lowered prepare registers from 128 to 126 without spilling and kept 5,979/5,979 hits, but matched early intervals were 0.65–0.85% slower. A block-uniform GLV12 selection with the same 12.5% share also kept 5,979/5,979 hits; early gains of 0.14–0.43% were small relative to clock differences, and the later hot interval slowed. None gave a defensible improvement near the new 1% floor, so this redraw retains the previously verified source.

An in-process CPU worker on/off check of the unchanged v2 binary used the controller's four alternating windows. With four workers, the CPU completed about 3.02–3.20 million candidates/s and all 39 tentative CPU hits checked exactly. The GPU batch interval with workers was 0.00436 versus 0.00437 s without in the first round, and 0.00602 versus 0.00603 s in a later hot round. Within the resolution of these short windows, the workers did not slow the GPU; disabling co-grinding would remove verified CPU work without a demonstrated GPU gain. This local controller measurement does not substitute for a ranked r5 run.

Moving the deferred ordinate subtraction one field multiplication earlier in the point-add tail preserved the first 2,979 GPU hits exactly. The source-matched control completed twenty sequences at 972.0 million/s from a 42°C start; the modified native image completed them at 967.0 million/s from a 43°C start, with nearly equal average SM clocks of 2229 and 2232 MHz. That −0.51% result rules out this small scheduling change for the current package. Moving that subtraction even earlier also preserved 2,979/2,979 hits but completed twenty sequences at 964.2 million/s from a 44°C start with a 2227 MHz average SM clock, versus the 972.0 million/s control at 2229 MHz; it too is excluded. A broader schedule moving the independent U2, P, PP, PPP and Q computations before the two-product slope multiply-add also preserved the first 2,979 hits and lowered registers from 128 to 126, but four alternating hot runs suffered large clock and temperature drift; without a reliable positive rate it remains outside the submitted source.

## GPU search and table geometry

Each GPU lane converts a candidate's double SHA-256 digest into scalar components, decodes signed fixed-base digits, gathers the corresponding points from a problem-specific fixed-base table, and folds them through the XYZZ chain. The GLV11 path normally uses six Q terms and five P terms. The GLV12 P path uses six P terms and one more addition, but omits two cold table gathers. The first six segments of the GLV11 and GLV12 layouts are byte-identical and both decoders telescope to the same segment-zero bias, so the two paths yield the same scalar multiple.

`QSB_PMIX12=16`, `QSB_PMIX12_N=2`, and `QSB_PMIX12_WARP=1` choose the GLV12 P path for two of every sixteen global warps, or 12.5% of candidates. The choice is warp-uniform, keeping each warp on one trip count. It is applied in both digit decode and chain consumption, so a lane reads the codes it produced. The unchanged other 87.5% of lanes use GLV11 P. `QSB_PDEC_Z=1` decodes the five-term P digits directly from the signed residual without materializing its magnitude; Q already uses the zero-decode form.

The gather-pipelined chain carries the deferred Y coordinate as a pair of field elements. `QSB_GATHER_EARLY=1` launches the Y half of the following point's table gather as soon as its previous buffer is dead, before the current two-product slope multiply-add. The X half follows after its previous value's last read. The native carrier uses a 64-byte L2 fetch granularity. `QSB_TBL_L2POL=1` leaves the 48 MiB hot prefix at normal eviction priority and marks cold-table gathers as early eviction candidates, so a cold streaming line is less likely to evict a hot record. This eviction hint is active in the sm_89 native image; the compute_52 fallback still computes the same mathematical values.

The pair-ordinate chain, low-limb square rewrite, shortened field carry glue, recovery-tail carry cuts, packed x-coordinate lazy add, and digest schedule steering come from the donor implementation. They are value-identical on the accepted path, or rely on the same extremely rare carry bound and exact host gate already documented by the donor. The host gate re-derives any GPU nomination with OpenSSL before it writes a hit. No candidate is published solely on the strength of the device's approximate checkpoint.

The native carrier header `qsb_carrier_sm89.h` is part of the source archive and was built by fkiene with CUDA 12.8.93 from the donor's source. Its reported cubin SHA-256 is `6ff9e582a80c583a32c59bd4b3a07650097246273d6279ccc219635f571fdf2a`; the prepare kernel uses 128 registers and the finish kernel 64, with no reported register spills. The current integration changes host code and CPU-only headers; the donor's device arithmetic and carrier bytes are preserved. The source can also fall back to the compute_52 JIT image when the native carrier cannot be loaded.

## Pipeline and memory behavior

The donor uses four in-flight slots, each with a four-million-candidate batch, in place of the promoted tree's two eight-million-candidate slots. Each slot owns its pipeline state, roots, checkpoint and readback. Both geometries reserve about one GiB for the four 16-byte state planes. The host drains a completed slot before reusing it and writes verified hits with their own sequence and locktime. The completion pipeline does not change candidate enumeration or the verifier's hit record format.

The integration adds an adaptive host batch length after the problem-specific GPU table and other fixed buffers are allocated, but before the four slot states are allocated. It asks CUDA for free device memory and keeps the donor's four-million batch when the slot states plus a 192 MiB reserve fit. Otherwise it halves the runtime batch length to two million or one million. Kernel launch dimensions, root dimensions, sequence advancement and CPU-controller batch accounting derive from that runtime length. This allows the same source to start on benchmark runners where other processes or driver state leave less free VRAM after the 21.6 GiB fixed-base table. The GPU still visits the same candidates; only grouping changes. The source defaults remain four slots and four million candidates, and the native device image is unchanged by this host calculation.

The fixed-base table depends on the benchmark problem's public curve inputs and is built for each problem. It is spot-checked against OpenSSL during setup. The active build uses the native carrier, the twenty-file original include closure, five additional CPU v2 helper headers, and the GPLv3 licence notices for the VanitySearch-derived headers. `build_carrier.sh` regenerates the native image from source. The carrier header is about 420 KiB. Older notes and research files may remain under `candidates/pinning/`, but `pinning.cu` does not include them and the ranked executable does not read them. The final packaged archive size should be checked against Yukon's 25 MiB compressed limit.

## Disjoint CPU work

The CPU co-grinder runs only for the normal single-hash, host-gated pinning search. GPU work walks sequences upward from `0x80000000`; CPU workers walk downward from `0xFFFFFFFE` over the same permitted locktime range, so their candidate sets remain disjoint for this timed search. Workers run at idle scheduler priority and the inherited controller measures available CPU share and GPU batch intervals, reducing workers when the GPU cost exceeds their added candidate rate. Every tentative CPU hit must pass the same exact OpenSSL gate before it is appended to `results/pinning_hit_cpu.txt`; the benchmark verifier then re-derives it again.

The CPU v2 engine replaces the earlier W16 engine. It uses an unsigned low window with the recovery point folded in, signed higher windows, and batched affine additions over 2,048 candidates. The CPU fixed-base table selects among approximately 1,216, 400, 160 and 72 MiB layouts using host and cgroup memory availability, falling back if allocation fails. Its SHA-256 paths are eight-lane AVX2 or two-way SHA-NI where available; its curve paths include AVX2 four-lane, BMI2/ADX scalar assembly and portable scalar code. A startup tuner selects supported paths on real batches. These are ercumentyildirim's mechanisms from PR #1731. Our integrated four-worker local comparison, reported below, confirms a CPU rate gain on this machine; it does not guarantee the same gain on a ranked runner.

The integration changes the CPU table helper's affinity before it spawns the table-builder threads. PR #1731 pins the GPU host thread to one logical CPU and reserves its sibling, but its table helper initially inherits that one-CPU affinity. Setting the helper to the non-host worker set in `cg_table.h` lets its child builders inherit the worker set while the GPU host stays pinned. This is a host-only startup fix; it does not modify candidate arithmetic. The GPU kernel image and the adaptive batch code are the same as in the W16 hybrid. CPU outputs are counted only through their own verified hit tuples.

## Limits and next steps

The native sm_89 carrier and four-slot geometry were copied as a complete donor implementation. A feature-by-feature speed attribution is not established by this integration, and the local GPU result on this machine may differ from a ranked runner with different CPU contention or GPU clocks. The v2 engine produced more independently verified CPU work than W16 in the local matched run; its exact gain on a ranked CPU remains unknown. CPU co-grinding helps only to the extent that its verified extra hits exceed any GPU slowdown. Adaptive batching is a robustness measure; when VRAM is constrained to a smaller batch, its rate may fall. A promotion of another pinning submission while this ticket is running raises the 1% threshold and should be checked before deciding on a redraw. Subsequent work can isolate individual GPU mechanisms or tune the CPU controller, but those changes require their own exactness and sustained-rate evidence.
