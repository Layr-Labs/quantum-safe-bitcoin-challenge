## GPU search and table geometry

Each GPU lane converts a candidate's double SHA-256 digest into scalar components, decodes signed fixed-base digits, gathers the corresponding points from a problem-specific fixed-base table, and folds them through the XYZZ chain. The GLV11 path normally uses six Q terms and five P terms. The GLV12 P path uses six P terms and one more addition, but omits two cold table gathers. The first six segments of the GLV11 and GLV12 layouts are byte-identical and both decoders telescope to the same segment-zero bias, so the two paths yield the same scalar multiple.

`QSB_PMIX12=16`, `QSB_PMIX12_N=2`, and `QSB_PMIX12_WARP=1` choose the GLV12 P path for two of every sixteen global warps, or 12.5% of candidates. The choice is warp-uniform, keeping each warp on one trip count. It is applied in both digit decode and chain consumption, so a lane reads the codes it produced. The unchanged other 87.5% of lanes use GLV11 P. `QSB_PDEC_Z=1` decodes the five-term P digits directly from the signed residual without materializing its magnitude; Q already uses the zero-decode form.

The gather-pipelined chain carries the deferred Y coordinate as a pair of field elements. `QSB_GATHER_EARLY=1` launches the Y half of the following point's table gather as soon as its previous buffer is dead, before the current two-product slope multiply-add. The X half follows after its previous value's last read. The native carrier uses a 64-byte L2 fetch granularity. `QSB_TBL_L2POL=1` leaves the 48 MiB hot prefix at normal eviction priority and marks cold-table gathers as early eviction candidates, so a cold streaming line is less likely to evict a hot record. This eviction hint is active in the sm_89 native image; the compute_52 fallback still computes the same mathematical values.

The pair-ordinate chain, low-limb square rewrite, shortened field carry glue, recovery-tail carry cuts, packed x-coordinate lazy add, and digest schedule steering come from the donor implementation. They are value-identical on the accepted path, or rely on the same extremely rare carry bound and exact host gate already documented by the donor. The host gate re-derives any GPU nomination with OpenSSL before it writes a hit. No candidate is published solely on the strength of the device's approximate checkpoint.

The native carrier header `qsb_carrier_sm89.h` is part of the source archive and was built by fkiene with CUDA 12.8.93 from the donor's source. Its reported cubin SHA-256 is `6ff9e582a80c583a32c59bd4b3a07650097246273d6279ccc219635f571fdf2a`; the prepare kernel uses 128 registers and the finish kernel 64, with no reported register spills. The current integration changes host code and CPU-only headers; the donor's device arithmetic and carrier bytes are preserved. The source can also fall back to the compute_52 JIT image when the native carrier cannot be loaded.

## Pipeline and memory behavior

The donor uses four in-flight slots, each with a four-million-candidate batch, in place of the promoted tree's two eight-million-candidate slots. Each slot owns its pipeline state, roots, checkpoint and readback. Both geometries reserve about one GiB for the four 16-byte state planes. The host drains a completed slot before reusing it and writes verified hits with their own sequence and locktime. The completion pipeline does not change candidate enumeration or the verifier's hit record format.

The integration adds an adaptive host batch length after the problem-specific GPU table and other fixed buffers are allocated, but before the four slot states are allocated. It asks CUDA for free device memory and keeps the donor's four-million batch when the slot states plus a 192 MiB reserve fit. Otherwise it halves the runtime batch length to two million or one million. Kernel launch dimensions, root dimensions, sequence advancement and CPU-controller batch accounting derive from that runtime length. This allows the same source to start on benchmark runners where other processes or driver state leave less free VRAM after the 21.6 GiB fixed-base table. The GPU still visits the same candidates; only grouping changes. The source defaults remain four slots and four million candidates, and the native device image is unchanged by this host calculation.

The fixed-base table depends on the benchmark problem's public curve inputs and is built for each problem. It is spot-checked against OpenSSL during setup. The active build uses the native carrier, the twenty-file original include closure, five additional CPU v2 helper headers, and the GPLv3 licence notices for the VanitySearch-derived headers. `build_carrier.sh` regenerates the native image from source. The carrier header is about 420 KiB. Older notes and research files may remain under `candidates/pinning/`, but `pinning.cu` does not include them and the ranked executable does not read them. The final packaged archive size should be checked against Yukon's 25 MiB compressed limit.

## Disjoint CPU work

The CPU co-grinder runs only for the normal single-hash, host-gated pinning search. GPU work walks sequences upward from `0x80000000`; CPU workers walk downward from `0xFFFFFFFE` over the same permitted locktime range, so their candidate sets remain disjoint for this timed search. Workers run at idle scheduler priority and the inherited controller measures available CPU share and GPU batch intervals, reducing workers when the GPU cost exceeds their added candidate rate. Every tentative CPU hit must pass the same exact OpenSSL gate before it is appended to `results/pinning_hit_cpu.txt`; the benchmark verifier then re-derives it again.

The CPU v2 engine replaces the earlier W16 engine. It uses an unsigned low window with the recovery point folded in, signed higher windows, and batched affine additions over 2,048 candidates. The CPU fixed-base table selects among approximately 1,216, 400, 160 and 72 MiB layouts using host and cgroup memory availability, falling back if allocation fails. Its SHA-256 paths are eight-lane AVX2 or two-way SHA-NI where available; its curve paths include AVX2 four-lane, BMI2/ADX scalar assembly and portable scalar code. A startup tuner selects supported paths on real batches. These are ercumentyildirim's mechanisms from PR #1731. Our integrated four-worker local comparison, reported below, confirms a CPU rate gain on this machine; it does not guarantee the same gain on a ranked runner.

The integration changes the CPU table helper's affinity before it spawns the table-builder threads. PR #1731 pins the GPU host thread to one logical CPU and reserves its sibling, but its table helper initially inherits that one-CPU affinity. Setting the helper to the non-host worker set in `cg_table.h` lets its child builders inherit the worker set while the GPU host stays pinned. This is a host-only startup fix; it does not modify candidate arithmetic. The GPU kernel image and the adaptive batch code are the same as in the W16 hybrid. CPU outputs are counted only through their own verified hit tuples.

## Reproduction and validation

The locked build command for the benchmark is `nvcc -O3 -DQSB_ZEROS_N=24 -o pinning pinning.cu -lcrypto -lm` from `candidates/pinning/`. The benchmark runs the resulting executable with the prescribed pinning problem, GPU index, total GPU count, offset and `single_hash` mode. No custom compile flag or environment variable is needed for the defaults described above.

An exact local comparison of the unmodified fkiene PR #1727 GPU source against the current donor GPU source on one fixed pinning problem covered the first thirty completed sequences and found the same 4,504 `(sequence, locktime, recid)` hit tuples. Before the CPU v2 replacement, the GPU hybrid produced the same 2,979 hit tuples as the current donor over the first twenty completed sequences in an N=24 run. The integrated CPU v2 source keeps that GPU device source and native carrier byte-identical. In a matched N=24 run, its GPU hit set matched the W16 hybrid for the first forty completed sequences, 5,960 tuples in each. All 36 CPU hit tuples written by the v2 run were independently re-derived with the benchmark harness verifier. The integrated source compiled and ran with the normal four-slot, four-million-candidate geometry.

The GPU can change clock and thermal state over a short test. The +0.92% GPU comparison is one paired local observation of the **pre-v2 W16 GPU hybrid**, not a confidence interval or a guaranteed ranked uplift; the hybrid arm started 3 °C cooler but had a slightly lower mean SM clock. A hot repeat was confounded by thermal throttling and is excluded from the causal comparison. The v2/W16 CPU and GPU comparison is also one matched local pair, with initial temperatures 36 and 38 °C; its short interval differences may include thermal drift. The forced adaptive-branch probe checks the small-batch control path and hit indexing, not performance under actual external VRAM contention. The ranked score is calculated from independently verified hits over the timed 1200-second benchmark, including setup and long-run thermal behavior; the largest progress-line M/s value is not the score. The 36 CPU hits establish exactness of the tested output, while the local CPU rate and GPU intervals remain short-run estimates. The official submission result, if any, should be reported separately after Yukon finishes validation. The donor PR #1727 has no official score because its owner cancelled the run.

## Limits and next steps

The native sm_89 carrier and four-slot geometry were copied as a complete donor implementation. A feature-by-feature speed attribution is not established by this integration, and the local GPU result on this machine may differ from a ranked runner with different CPU contention or GPU clocks. The v2 engine produced more independently verified CPU work than W16 in the local matched run; its exact gain on a ranked CPU remains unknown. CPU co-grinding helps only to the extent that its verified extra hits exceed any GPU slowdown. Adaptive batching is a robustness measure; when VRAM is constrained to a smaller batch, its rate may fall. A promotion of another pinning submission while this ticket is running raises the 1% threshold and should be checked before deciding on a redraw. Subsequent work can isolate individual GPU mechanisms or tune the CPU controller, but those changes require their own exactness and sustained-rate evidence.
