# Pinning: predicated cache-policy gathers in the GLV12 pipeline

This submission changes only the pinning candidate. It combines the public
predicated constant-policy table gathers from dukemawex's [PR #1775](https://github.com/Layr-Labs/quantum-safe-bitcoin-challenge/pull/1775)
with that PR's phi-hoisted chain loop, then integrates both into our previously
submitted adaptive-batch GLV12 GPU and CPU v2 co-grinder. The implementation
preserves the candidate arithmetic, the host OpenSSL publication gate, and the
benchmark's input and output contract. The native sm_89 image is regenerated
from the changed device source. This is a performance hypothesis tested locally;
only Yukon can establish a ranked score or promotion.

## The changed hot path

The prepare kernel repeatedly adds signed fixed-base table points to a
projective accumulator. The table has a 48 MiB frequently reused prefix and
several GiB of colder records. Its existing policy loads cold records with
`evict_first` and hot records with `evict_normal`, preserving the prefix in L2
more often. Previously each 16-byte gather used a per-lane policy select. The
compiler copied that policy into uniform registers repeatedly inside the
one-add chain loop, adding policy selection and `R2UR` instructions near the
loads. The four loads also issued late in the trip.

`QSB_TBL_POL_PRED=1` replaces each 16-byte load with complementary predicated
loads using two compile-time policy descriptors. Each lane executes one side
of the pair: the record index at or above `QSB_HOT_RECS` uses the cold
descriptor; an index below it uses the hot descriptor. The table address and
destination registers are the same on both sides. The first Y-half load keeps
the existing 64-byte L2 fetch hint; the X half and the second Y-half load keep
their previous cache-hint behavior. A policy affects eviction, not the bytes
read. `QSB_TBL_POL_PRED=0` keeps the original selection form for comparison.

`QSB_PHI_HOIST=1` moves the once-per-candidate endomorphism scale out of the
rolled one-add body. The first pass ends immediately before the P-side term,
performs that same multiplication, and a second pass continues the same loop.
The multiply therefore still occurs exactly once and immediately before the
same table term. `QSB_PHI_HOIST=0` retains the prior loop. This companion
change narrows the loop instruction footprint; it is not assumed beneficial in
isolation. An isolated 45°C local test of phi hoisting alone was 0.32–0.45%
slower in three hot intervals. The combined source must earn its place through
the measured gather change, not an instruction-count claim.

The native sm_89 cubin generated by `build_carrier.sh 24` matches the device
image reported in PR #1775 (cubin SHA-256 beginning `9aafe9d7f1eed411`).
The prepare kernel uses 128 registers and the finish kernel 64; the build
reports no spills. PR #1775 reports about 997 SASS instructions in its hot
loop, versus 1007 with phi hoisting alone and 1117 in the starting loop. More
important to this hypothesis, its cold gathers move earlier in the loop. A
shorter static loop is not itself evidence of a faster 20-minute grind.

The full GPU table still depends on the fresh problem's public curve inputs.
Our host chooses four four-million-candidate slots when its memory reserve
fits, then reduces slot length to two million or one million if free VRAM is
tight. The same runtime batch length controls launch dimensions, candidate
indexing, sequence advancement and readback. This adaptive path is relevant
because the two donor predicated-gather tickets ended on an r3 runner at the
Benchmark step with zero candidates, before any useful speed comparison. Our
integration retains the host fallback that previously ran on r3, while a new
ranked ticket must still demonstrate it on its assigned runner.

## Local correctness and rate evidence

The native carrier and normal host executable built with CUDA 12.8 and the
ranked build flags:

```sh
cd candidates/pinning
bash build_carrier.sh 24
nvcc -O3 -DQSB_ZEROS_N=24 -o pinning pinning.cu -lcrypto -lm
```

On the committed public pinning problem, with CPU workers disabled in both
arms to isolate the GPU, the combined device source and the prior source
produced **the same 5,960 distinct GPU hit tuples through the first 40
completed sequences**. The comparison key was `(sequence, locktime, recid)`.
The first combined run began at 34°C and the first control at 38°C, so its
roughly one-percent raw lead was thermally confounded. We did not use that
number as a projected ranked uplift.

A second same-problem pair began at approximately 45°C in both arms. The
combined source's cumulative reported processing rates through sequence
10/20/30 were **980.3/975.1/966.8 million/s**; the control's were
**974.5/968.9/960.9 million/s**. In the later sequence-20-to-30 interval,
the combined source completed about 950.62 million/s versus 945.29 million/s,
a **0.56% local GPU gain**. These are short-run processing rates from the
grinder's progress lines; they are not the official score. Temperature and
SM-clock samples put both later intervals near the same hot operating point,
although residual clock and temperature noise remains. The source is worth a
ranked trial on this evidence, but a 0.56% GPU gain alone does not guarantee
the one-percent promotion threshold. The CPU v2 engine can add verified work
relative to the promoted W16 source, and the official hit estimate has
sampling noise. Neither is a claimed ranked improvement until Yukon reports it.

The host gate re-derives every tentative GPU or CPU hit with OpenSSL before
publication. The benchmark then verifies all published hits independently.
The exact early hit-set comparison checks the changed load path and phi
schedule on one fixed problem; it does not prove every late candidate or a
fresh randomized problem. The cache policy has no mathematical effect, and
the phi control-flow transformation is intended to keep the same term order.
The official randomized run is the decisive correctness and performance test.

## How to reproduce and interpret the result

From the Yukon pinning work directory, run `yukon setup --track pinning` and
`yukon run --track pinning`. The benchmark owns its clock, generates a fresh
problem after submission, verifies each published hit, and estimates
throughput from verified hits and elapsed time. The progress-line peak, SASS
instruction count, and our local 30-sequence intervals must not be used as
substitutes for that score. The benchmark archives only `candidates/pinning/`.
No benchmark, verifier, input generator, problem instance or subset candidate
is changed by this pinning submission. The source keeps the normal 24-bit
ranked difficulty and `single_hash` invocation contract.

The main uncertainty is long-run performance on the assigned 4090 runner.
The 21.6 GiB fixed-base table and four slot buffers can leave little free
VRAM; CPU quota, runner clocks, cooling and problem-specific hit noise differ
from the local screen. A failed donor run with zero candidates supplies no
ranked performance evidence. If the official ticket does not improve the
frontier, its diagnostic CPU/GPU split and runner identity should guide the
next isolated change rather than reinterpreting a short local rate as a win.
