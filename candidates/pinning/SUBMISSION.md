# Pinning: overlap the first low-density GLV table read with point addition

This pinning-track source candidate was prepared with GPT 6 Sol in Codex. The source derives from our PR #1205 and carries forward its 50 MiB persisting-L2 policy, host slot overlap, dense-first table layout, register-held seed codes, and exact host publication gate. It adds an exact seed X3 sign rewrite and moves the first segment-1 table read earlier in the fixed-base accumulation. There is no local RTX 4090 throughput measurement of this combination. Its official Yukon run will decide whether it clears the current leaderboard gate.

## Measured frontier and reason for this experiment

The promoted pinning source is `b59484345df5208f5caffc82c25a4a3b50cbe523` at 826,926,066 verified candidates/s. Our PR #1205 measured 829,282,307 verified candidates/s on `intel-r5-54598`, missing the 835,195,327 promotion floor. Its self-reported peak was 852.2M candidates/s, which is a different metric from the official verified score. The intervening PR #1223 combined a smaller 42.166 MiB persisting window and one L2 prefetch; it scored 793,354,720 on `leadergpu-3568275`, a different host. That result is not a controlled throughput comparison against PR #1205. The current source restores the PR #1205 50 MiB window and device set-aside and replaces the optional prefetch with a real early record load.

The fixed-base GLV path adds fourteen signed table points to an accumulator. Under the normal nonzero-Q path, term 7 is the first point from the second GLV half and term 8 is the next. The table record for term 8 is already known from the scalar recoding before term 7 is consumed. Previously the record was loaded only after term 7's point addition, or given a nonbinding L2 prefetch hint in PR #1223. This candidate requests the record's x and signed y during term 7 and delays their consumption until term 8. It aims to place global-memory latency behind the independent field arithmetic of term 7. It leaves the point sequence, table indices, and field arithmetic unchanged. The practical gain may be too small, and scheduling or shared-memory traffic may offset it.

## Changes and exactness

`QSB_C1_EARLY_X=1` brings term 8's four x limbs into registers at term 7, after the existing term-7 point load and before its point addition. `QSB_C1_EARLY_Y_SHM=1` also loads the four signed y limbs and parks them in the unused upper part of each thread's digit-arena shared-memory allocation. At term 8, x comes from the registers and y from shared memory. The existing `QSB_C1_PREFETCH` hint is bypassed when the early load is on, so the candidate does not issue redundant prefetch traffic. Both switches can be disabled at compile time; disabling both and `QSB_C1_PREFETCH` restores the old load schedule. The 42 MiB L2 controls remain separately compilable but default to zero, restoring PR #1205's 50 MiB policy.

The signed y transformation is the same as `gt_load_signed_flat_m`: a sign mask from the shared digit code XORs each limb, with the same conditional carry sequence if `QSB_YOFF=0`. The default `QSB_YOFF=1` uses the table's offset ordinate and only XORs. The physical table record is selected by the same masked absolute index, `code & 0x1fffff`, so the dense-first permutation and logical segment lookup are unaffected. The early scratch begins after all fourteen 32-bit digit-code planes: byte offset 7,168 in a 12,288-byte shared arena for 128 threads. Four 64-bit values per thread occupy another 4,096 bytes, ending at byte 11,264. A compile-time assertion checks the bound for the supported block sizes. Each thread writes and reads its own lanes without requiring a new barrier.

If the Q half is zero, the accumulator starts with the P0 and P1 seed points and the loop starts at term 9. It never consumes the early term-8 buffer. If both halves are zero, the early path is skipped entirely. With nonzero Q, term 7 always precedes term 8, so the scratch and register values are initialized before use. The exact seed-fusion rewrite already present in this branch changes the way the first pair's signed X3 is formed; its projective identity was checked on 4,096 edge tuples and 10,000 random tuples. The pre-existing rare seed-multiply carry cut inherited from PR #1205 remains a lossy optimization. The exact host recheck stops wrong GPU hits from being published but does not recover a genuine hit skipped by an approximation.

All executable changes are under `candidates/pinning/`. No subset file, benchmark script, scorer, verifier, problem input, or workflow is edited. The earlier setup-only spot-check fix from PR #1223 remains: segment 6 has a non-power-of-two length and is sampled by modulo, so setup covers its full range. It does not enter the timed stage-0 kernel. The regular `./setup.sh pinning` and `./benchmark.sh pinning` interfaces remain in place. No generated binary, PTX, SASS, output hit list, or fixed answer is included in the submission.

## Validation performed

CUDA 12.6 in a Linux arm64 build container compiled the ranked `QSB_ZEROS_N=24` source for native `sm_89` using `nvcc -O3 -arch=sm_89 -Xptxas=-v`, linking the normal OpenSSL and math libraries. The full early-load stage-0 kernel used 120 registers and 12,288 bytes of shared memory with zero stack frame and zero spill loads or stores. A matched 50 MiB control with both early-load switches and prefetch off used 114 registers, the same shared allocation, and zero spills. An x-only version used 128 registers and zero spills. Both the full and control builds fit four 128-thread stage-0 blocks within the 65,536-register budget on an RTX 4090; this is a resource calculation, not an occupancy trace. The full version adds roughly 40 static SASS instructions compared with the matched control, primarily for the extra path and shared-memory staging. Static counts do not predict executed throughput.

`test_seed_fuse.py` passed 14,096 algebra cases; `test_host_gate.py` checked the host publication algorithm, 64 SHA midstates, and recovery parity. The record-load helpers and control flow were checked against the existing full loader and the Q-zero path. The current code and public note passed `git diff --check`. The native compile and host tests establish neither GPU numerical parity nor 4090 speed. This machine has no NVIDIA GPU or driver, so the official ranked run is the first end-to-end device correctness and performance measurement of the exact package.

For reproduction, run `nvcc -O3 -DQSB_ZEROS_N=24 -o pinning candidates/pinning/pinning.cu -lcrypto -lm` for the organizer-style build. Add `-arch=sm_89 -Xptxas=-v` for the native resource check. Put binaries and logs outside `candidates/pinning/`. A useful target-card comparison would run the same problem with `QSB_C1_EARLY_X=0`, `QSB_C1_EARLY_Y_SHM=0`, and `QSB_C1_PREFETCH=0`, then with the candidate defaults, alternating order and checking the exact verified hit set, actual table-load sectors, L2 hit rate, DRAM bytes, and verified candidates/s. No such local comparison is claimed here.
