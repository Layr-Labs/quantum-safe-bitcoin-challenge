# Pinning: dense L2 reserve and early segment-1 prefetch

Effort: xhigh. This pinning-track candidate was prepared with GPT 6 Sol in Codex. It extends our earlier PR #1205 implementation, whose official RTX 4090 run verified 118,783 hits over 1,201.5498 seconds and scored 829,282,307 verified candidates per second. That result exceeded the 826,926,066 promoted source but missed the 835,195,327 100-bip promotion threshold. The new memory-service choices below are a follow-up experiment, not a claim that the threshold has already been reached. The selected source is the committed `5ed465136833f5bb9514c851a719c884a93419e4` implementation in this archive lineage.

## Goal and measured starting point

The promoted source commit is `b59484345df5208f5caffc82c25a4a3b50cbe523`. The earlier PR #1205 moved the seven GLV table segments into the physical order `[2,3,4,5,6,0,1]`, retained the exact host publication gate, overlapped independent sequence slots, kept two Q-side seed codes in registers, and used a rare carry cut in one speculative seed multiply. Its measured 829.282M/s rate is the direct starting observation for this branch. The run does not isolate the table-layout gain from its other changes, and its 852.2M/s reported peak is not the ranked score. This package keeps that search family and adds two switchable L2-service changes.

The 14-term fixed-base GLV table contains 1,215,139 records of 64 bytes, or 77,768,896 bytes (74.17 MiB). Logical segments 2 through 6 occupy the first 690,851 physical records, or 44,214,464 bytes (42.166 MiB). They receive more lookups per byte than the two larger low segments. PR #1205 requested a 50 MiB persisting-L2 access window and a 50 MiB device set-aside: the window covered all of segments 2 through 6 and the first 128,349 records of segment 0. The present branch requests a window ending exactly after segment 6 and a matching 42.166 MiB set-aside. It gives normal cache allocation more capacity for segments 0 and 1, whose combined size is 32 MiB. NVIDIA treats both the stream access-policy window and device limit as hints; the actual L2 hit rate can only be measured on the target card.

## Exact source changes in this package

All executable edits are in `candidates/pinning/pinning.cu`. `QSB_L2_DENSE_WINDOW=1` sets the default stream and both nonblocking slot streams' persisting access-policy windows to the 42.166 MiB dense prefix. `QSB_L2_DENSE_RESERVE=1` requests the same number of bytes from `cudaLimitPersistingL2CacheSize`. Each can be set to zero independently to restore the earlier 50 MiB request. The feature applies only with the dense-first physical table layout. The byte length and base pointer remain within the table allocation.

`QSB_C1_PREFETCH=1` issues one `prefetch.global.L2` for term 8, the first segment-1 record outside the dense prefix, while term 7's point addition is still pending. The record code is already materialized in the per-thread shared digit arena. The prefetch address is computed from that code's existing absolute physical record index, with the sign bit masked off, and is not dereferenced by the prefetch helper. `QSB_C1_PREFETCH_SECOND_SECTOR=0` is the default; setting it to one issues a second hint 32 bytes later. `QSB_C1_PREFETCH=0` disables the hint. Every record remains loaded through the unchanged `gt_load_signed_flat_m` path when actually consumed, so prefetch affects scheduling and cache state, not point arithmetic or output identity.

The setup-only OpenSSL spot checker also now samples the final GLV segment with modulo rather than a power-of-two mask. Segments 0 and 1 have 262,144 entries, segments 2 through 5 have 131,072, and segment 6 has 166,563. The old mask did not sample the nonpower final segment uniformly. The GPU table builder, spot checker, and OpenSSL fallback all address records through `gt_offset(ch)` and `gt_entries(ch)`. The seven physical intervals are disjoint and cover indices 0 through 1,215,138 exactly. The fallback's record placement and the consumer's sign handling remain unchanged. This spot-check adjustment affects setup validation only and does not enter the timed stage-0 kernel.

The candidate does not edit the sibling subset track, benchmark harness, scorer, verifier, problem generator, workflow, or setup and benchmark commands. It contains no prebuilt cubin, PTX, hit list, solution, or evaluation fixture. The usual `./setup.sh pinning` and `./benchmark.sh pinning` interfaces apply.

## Validation and its limits

I compiled both the all-on and all-off variants with CUDA 12.6 for native `sm_89`, using `nvcc -O3 -arch=sm_89` and the normal OpenSSL/math link libraries. Stage 0 uses 122 registers, 12,288 bytes shared memory, a zero-byte stack frame, and zero spill stores or loads in both builds. The on version emits one `CCTL.E.PF2` prefetch instruction. The other compiled kernels also had zero spill stores and loads. The code and note passed `git diff --check`. The build artifacts stayed outside the editable candidate path.

The focused host-side checks passed: `test_host_gate.py` exercised 64 midstate/recovery samples and confirmed the exact host publication algorithm; `test_priority_pipeline.py` passed five dependency, slot reuse, partial batch, rollover, and error-injection tests; `test_slot_readback.py` passed three capacity, reuse, overlap, and error tests. `test_carry62.py` completed its boundary and random carry audits. These checks do not execute CUDA on the ranked GPU. A separate static audit confirmed that the prefetch's masked absolute record index is within the table range for term 8 and that the stream-window byte range ends within the allocation.

This Mac has no NVIDIA GPU or driver. The arm64 CUDA build establishes target-code viability and spill counts, not RTX 4090 throughput, L2 sectors, memory traffic, clocks, power, or the verifier's run score. The two cache changes could improve latency hiding, do nothing, or lose performance through hint traffic and eviction. The 42.166 MiB choice removes a persistence hint from part of segment 0; the ordinary L2 may or may not retain those records better. Only the organizer's trusted run decides promotion. The previously measured 829.282M/s is for PR #1205, not this package, and no percentage improvement is projected from static instructions.

## Reproduction and follow-up

From this source, build with `nvcc -O3 -DQSB_ZEROS_N=24 -o pinning candidates/pinning/pinning.cu -lcrypto -lm`. For a native target resource check add `-arch=sm_89 -Xptxas=-v`. Place outputs outside `candidates/pinning/`. The independently switchable controls permit a four-way comparison: both cache changes off, dense window/reserve only, prefetch only, and both on. A matched fixed-work RTX 4090 comparison should use the same problem and alternate order, count verified hits, compare peak and official candidates/s, and collect L2 sector hit rate and DRAM read bytes. This ranked submission tests the both-on choice once; it is not an unchanged redraw of PR #1205.
