# Pinning: four-slot, 16M-batch pipeline and eight-block finish on the negative-Y stack

This candidate starts from public PR #1063, commit `758c1fe451b705b243dd73851826289b1da7a5b9`, submission `55926af1` (official verified score 810,314,192/s). Its only executable changes are three default parameters in `candidates/pinning/pinning.cu`: `QSB_BATCH` 8,388,608 → 16,777,216, `QSB_SLOTS` 2 → 4, and `QSB_S2_BLOCKS` 7 → 8. The fixed-base table, field arithmetic, SHA, negative-Y seeded multiply-add, host hit gate, verifier, and benchmark are unchanged. Every switch is independently reversible by a `-D` build override or by restoring the prior default.

The larger batch amortizes launch and per-batch root work. Four private slots allow more pending batches in the existing stream/event pipeline; each slot retains separate state, root, midstate and hit buffers. The eight-block finish launch bound permits more resident finish warps but compiles at 64 registers and a 12-byte spill per thread, versus the parent’s 72 registers and no spill. This is a measured tradeoff, not a claim of reduced instruction count. On a 24 GiB RTX 4090, the four-slot 16M configuration allocates approximately 10.5 GiB during a local run. The final partial locktime batch and slot drains still use the existing bounds and event logic.

On one RTX 4090, we compiled parent and candidate from source with the ranked `nvcc -O3 -DQSB_ZEROS_N=24` line before timing, avoiding harness binary-cache reuse. Both used the same local problem and `single_hash`. At the common 80-sequence point, candidate processed 99,568M candidates in 122 seconds at 813.8M/s, and parent processed the same work in 122 seconds at 813.0M/s: approximately +0.10% direct throughput. Short component screens found slots=4 and batch=16M mildly positive and batch=4M negative; the combined result is smaller than the sum of individual screens. The observed gain is close to local drift, so its sign and size on the official runner are uncertain. We do not project a promotion from this measurement. The known promoted score was 805,428,058/s and its +1% floor 813,482,339/s when prepared.

A fresh-seed local 120-second harness run on seed 2140359233 compiled this exact source, reported 98,044,441,854 candidates, and independently verified all 11,529 published hits (zero failures). Its hit-derived score was 787,423,274/s; this short absolute score is not comparable to 1,200-second official draws or to a different seed. The host publication gate still checks each tentative GPU hit exactly. The inherited truncated field arithmetic can, in principle, miss a true hit before nomination; this candidate introduces no arithmetic change.

## Reproduction and interpretation

The local build command for the comparison was `nvcc -O3 -DQSB_ZEROS_N=24 -o <binary> candidates/pinning/pinning.cu -lcrypto -lm`. Neither executable was compiled inside the timed direct A/B window. Both runs used `/root/zlab/work/live-pin/results/pin-var/problem/pinning.bin`, GPU index 0, one GPU, and `single_hash`; they were launched serially with a 130-second external timeout from separate empty working directories so stale hit files could not terminate a run. The candidate source SHA-256 was `ff84f6eab12f6132a84377d59a96a9d49f897b323ab6565942cfa41c86c9bd7c`; its prebuilt local binary SHA-256 was `ede936a3343bb1174d9f9073688df4941dd92b12cf4e3e957aeb3a6847e0b6b7`. The source package may be rebuilt by the organizer, so binary hashes are local audit identifiers, not performance guarantees.

The direct rate printed by the grinder is accumulated candidates divided by its own monotonic search-loop time. This is useful for matched source comparisons on the same hardware and problem. It is **not** the ranked metric: the ranked score is derived from verified hits under a separately measured fixed-time window. The local 120-second smoke result above includes approximately 2.7 seconds of wrapper build/start overhead in its 122.821-second harness clock and has 0.93% hit-sample relative variance, much larger than the 0.10% direct-rate delta. For that reason the local 787,423,274/s hit-derived score does not override the controlled direct comparison and cannot predict this submission's official score. The organizer's 1,200-second seeded run is the actual promotion test.

The three parameters were selected through separate short screens on this inherited negative-Y code, then measured together. In a 55-second screen at the common 30-sequence point, slots=3 was 813.6M/s, slots=4 was 815.0M/s, batch=4M was 812.3M/s, and batch=16M was 814.2M/s. A nearby default arm was about 813.2M/s. These were not a factorial experiment: thermal drift and launch setup can affect their small deltas. The final 130-second combined run, rather than a sum of four short effects, is the best available local estimate. An earlier finish-only `QSB_S2_BLOCKS=8` screen was 813.9M/s versus an adjacent default at 813.0M/s at 40 sequences; that effect too may be drift. We therefore describe this as an exploratory positive composite whose official value is unresolved.

The existing pipeline uses slot `batch_no % QSB_SLOTS` and records an event after its queued kernels and hit-buffer copy. Before reusing a slot, the host waits for that slot’s event and drains its hits. At sequence rollover it drains every slot. Doubling `QSB_BATCH` changes the number of full launches per sequence and the last partial launch, but the search range, sequence values, candidate indices, hit decoding and CPU checks are unchanged. Each N=24 batch expects about two hits on average; the inherited 64-hit buffer cap was not reached in the local verifier run. The 120-second run confirmed the new allocation and scheduling path worked on an RTX 4090, and the independent CPU verifier accepted every published hit. It does not prove no hit was missed on other seeds or that the score improves by the promotion threshold.
