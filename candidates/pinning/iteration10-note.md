## Reproduction and implementation summary

This is a bounded schedule-specialization experiment, not a claim that a new cryptographic primitive has been devised. The only tracked implementation edit changes the default definition of QSB_SPARSE_TAIL from 0 to 1 in candidates/pinning/pinning.cu. The implementation already exists in the same translation unit. Attribution is preserved in the source comments. All other compilation defaults remain unchanged. In particular, this experiment does not enable the streaming memory option and does not add an architecture flag. This separation matters because changing several independent mechanisms would make the resulting timing difficult to interpret.

The specialization consumes the same eight-word SHA chaining state as the generic compression function. It receives three dynamic words and initializes words 3 through 14 to zero, with word 15 equal to 9995 times eight. It performs the initial rounds using literal zero addends where possible. The first expanded schedule group is explicitly simplified for that shape; subsequent groups invoke the existing generic SHA256_RND and WMIX macros. The final eight additions feed the working registers back into the original chaining state. No hit filtering, candidate counting, stopping condition, probability threshold, or verifier logic is changed.

Selection is guarded by the existing host predicate: single_hash must be true, easy mode must be false, suffix length must be 75, sequence offset must be 31, locktime offset must be 67, and total preimage length must be 9995. When this predicate is false, the existing generic path is retained. The fixed words uploaded by the host incorporate suffix bytes 64 through 66, byte 71, bytes 72 through 74, and the padding byte. The kernel patches locktime bytes into the first two words. The device constant upload already checks cudaMemcpyToSymbol and returns an error if the upload fails. The edit does not add allocations, cleanup obligations, or new launch configurations. Existing inactive-lane and batch boundary handling is unchanged.

The technical hypothesis is that removing operations whose operands are known zero can reduce compression work without changing the digest. A limitation is that the compiler may already simplify much of the generic schedule, or the shortened schedule may produce less favorable register lifetimes. Moreover, SHA compression is only part of the public-key recovery pipeline. A reduction in SHA instructions need not translate into a material end-to-end throughput gain. This experiment measures the complete grinder rather than assigning a synthetic speedup to the affected function.

## Commands and environment

Work directory: quantum-safe-bitcoin-challenge, the existing pinning checkout. The local OpenSSL dependency root is the sibling local-deps/root directory. Export CPATH to its usr/include and usr/include/aarch64-linux-gnu subdirectories. Export LIBRARY_PATH to its usr/lib/aarch64-linux-gnu directory and prepend the same directory to LD_LIBRARY_PATH. These settings are local build dependency resolution, not changes to the submitted verifier.

Explicit compilation was performed with the repository Python helper:

    python3 -c 'from pathlib import Path; from harness.gpu_wrap import compile_kernel; compile_kernel(Path("candidates/pinning/pinning.cu").resolve(),24)'

The retained compilation log shows nvcc -O3 -DQSB_ZEROS_N=24 with -lcrypto -lm. The local verifier command was:

    QSB_GRINDER='cmd:python3 harness/gpu_wrap.py --src candidates/pinning/pinning.cu --no-build' QSB_SECONDS=120 QSB_OUTPUT_DIR=benchmark-results/iteration10-sparse ./benchmark.sh pinning

The wrapper reused the just-built executable. Seed 1123355314 was generated by the benchmark rather than supplied by the candidate. The benchmark reported 8,716,121,334 self-reported candidates, 957 verified hits, and 120.3 seconds on the harness clock. Self-reported throughput was 72.5 million candidates/s; it is not the scored quantity. The score instead uses the verified hits and the N=24 success probability, yielding 66,759,232 verified candidates/s. The relative uncertainty of 0.032325 was below the configured 0.1 limit. All 957 submitted hits verified. These are local diagnostic results only.

The preceding retained baseline log has 1003 verified hits, 69,976,205 verified candidates/s, and a self-reported rate of 71.3 million/s. The raw rate and verified-hit score move in opposite directions between these two samples. Neither comparison establishes a statistically secure causal speedup. The local score is supplied to the platform honestly, even though it is below the previous diagnostic and far below the reported remote frontier. No extrapolated remote score is claimed.
