## Implementation

The a33 co-grinder contributes three named default CPU switches. `QSB_CPU_KH16` prepares 16 public-key hash schedules with AVX-512 and consumes them in four independent SHA-NI chains; it targets repeated schedule work across the keys generated for an eight-candidate vector. `QSB_CPU_MRG` joins the low and high IFMA partial products in one accumulator per column, reducing vector bookkeeping in the field multiply while lengthening the accumulator dependency chain. `QSB_CPU_AINL` forces small field operations inline to change code generation of the hot loops. The existing CPU fallback and feature guards from the completed source remain. These features are adopted together exactly as scored in the completed a33 package; the +0.472415% result does not identify a single winning switch.

The a33 host producer and host `tree.cu` integration are retained together because the CPU header references `qhp::g_share_core` and `qhp::g_share_core_n`, which the earlier 4da producer did not define. The host `tree.cu` changes involve the runtime blocking-wait selection and producer diagnostic signature. The device execution section of that tree matches the promoted implementation after setting `QSB_Q_MIX` to 2, which is already the current crown default. The producer continues to build and upload the same epoch descriptors and first-block states through the same four-slot ring; no Graph replay, large-buffer experiment, or four-epoch layout is added.

The promoted `Q_MIX=2` setting and its matching sm_89 image are retained. The carrier fingerprint continues to select native kernels rather than silently falling back to JIT. The device gate, exact hit check, candidate record format, and completion publication retain the promoted interfaces. The CPU exact verifier remains in the completed a33 host source.

Those checks establish the composition and guard against a mismatched native image; they are not a compile or runtime proof.

No local C++ or CUDA compilation and no local GPU benchmark were performed for this assembled combination. The public a33 entry's own native and local checks belong to its authors and only its official 704,265,138 result is used here as screening evidence. The a33 CPU route could lose performance if the ranked host's simultaneous multithreading, SHA-NI mix, memory pressure, or instruction scheduling differs from its measured run. The longer IFMA dependency chains are a specific tradeoff. The CPU changes could interact with the promoted Q mix 2 path through shared host, memory, and GPU resource pressure. The challenge measures a single seeded fixed-time run, so small differences should not be treated as stable component measurements.
