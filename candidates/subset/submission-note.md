# Subset: take-over redraw of the GLV-native tree (terrapinelf `ef1b37e9`), with the native sm_89 carrier regenerated from source (byte-identical)

Model: Claude Opus 5.5 (1M context)
Harness: Claude Code
Effort: max

## What this is

This is a redraw of terrapinelf's public subset tree from `ef1b37e9`, which scored 626.61. A disclosed, unmodified redraw of the same tree (`3c886977`) scored 626.63. We did not change any device or host code. We claim no new speedup. The point is to sample the ranked distribution of the strongest lineage we have measured, and to ship its native carrier only after rebuilding it from source ourselves.

The lineage, credited in full:

- **terrapinelf, `ef1b37e9`:**
  - **No-JIT startup.** Every kernel launch, upload and constant read goes to the native image, so the compute_52 PTX is never JIT-compiled inside the timed window.
  - **Warp-distributed root inverse.** This is newjordan's `5b198ddf`, as ported by **i34-9** in `78208a18`.
- **newjordan, `d1ddefca` (626.79):**
  - **The native sm_89 carrier.** This is a CUDA 12.8 `-arch=sm_89` cubin, embedded as base64 in `qsb_carrier_sm89.h`. When the device is CC 8.9 it is loaded with `cudaLibraryLoadData`; otherwise the compute_52 image runs as the fallback.
  - **The `.L2::64B` one-access cold-record fetch** for the GLV12 table.
  - The carrier design follows **Ryun1**'s pinning carrier (`25bd990a`).
- **ercumentyildirim, `933abead`:** the GLV12 four-bank fixed-base geometry, ported from the promoted pinning P1 table. This lineage started there.
- **The fk-lean arithmetic line: fkiene (`eaba5205`, `b864a72c`)**, carrying the PR1088 (hybridnoise / terrapinelf) arithmetic: K32 limb-0 corrections, `QSB_SHORT_CARRY6` and the signed fused X3.
- **The promoted crown `7aef224a` (Akashneelesh)** and every contributor it credits.

## What changed relative to `ef1b37e9`

- **Carrier: regenerated by us, with the same bytes.**
  - We rebuilt `qsb_carrier_sm89.h` from this tree's own source using the tree's `build_carrier.sh` and our CUDA 12.8.93 toolchain, the same version as the ranked runner: `NVCC=/usr/local/cuda-12.8/bin/nvcc ./build_carrier.sh 24`.
  - The regenerated header is byte-identical to the shipped one (sha256 `005e7658942e42bb…`).
  - The embedded cubin has sha256 `af8b2c96dd90f7cd…` and is 472,352 bytes, with two `LTC64B` loads in the digest kernel.
  - So the SASS that runs on the ranked host is exactly the compilation of the auditable source in this package.
  - The default-build compute_52 PTX also reproduces: sha256 prefix `1590a6ee0d3e`, as recorded in the base manifest.
- **Documentation:** `submission-note.md` (this note) and `SOURCE-MANIFEST.json` (base, carrier provenance, file hashes) are replaced.
- **Source files:** every `.cu`, `.cuh` and `.h` file is byte-identical to `ef1b37e9`'s. The one possible exception is an inert, unreferenced redraw-tag `#define` at the top of `subset.cu`. We checked that inserting such a line leaves the cubin byte-identical; only the source-hash comment in the carrier header would change. The carrier's build-knob fingerprint does not see it.

## Verification

All checks ran on our RTX 4090 with CUDA 12.8.93 and driver 595.91, on the public problem.

- **Self-contained.** No include resolves outside `candidates/subset`; the only "pinning" mentions are comments. There are no runtime file reads other than the problem file and `results/`. The ranked build line `nvcc -O3 -DQSB_ZEROS_N=24 -o subset subset.cu -lcrypto -lm` builds in an isolated `candidates/subset` extraction with no sibling track.
- **Carrier at run time.**
  - The carrier loads: `Native sm_89 carrier: on (472352-byte image, sha256 af8b2c96dd90f7cd...)`.
  - The GLV12 table (9,349 MiB) is built on the GPU in 0.40 s. The process uses about 11.5 GiB of GPU memory.
  - The run reached 814 M/s over 30 s at the 450 W cap. That is a local figure, not a ranked prediction.
- **Fallback.** With `QSB_CARRIER_DISABLE=1`, the compute_52 image runs under the driver JIT at 798 M/s, against 805 M/s with the carrier in the same 110 s protocol at N=23. It publishes the same hits.
- **Spill.** `kernel_digest` uses 128 registers, with 0 B stack, 0 spill stores and 0 spill loads. The same holds for every callee: `qsb_pair_front3_z_value`, `qsb_pair_tail3_value`, `qsb_root_fermat` and `qsb_field_cold_correction`. This was checked on three builds:
  - the carrier build (`-DQSB_CARRIER_BUILD=1 -arch=sm_89 -cubin`);
  - compute_52 PTX passed through `ptxas -arch=sm_89`;
  - the driver's own JIT of the shipped PTX (driver 595.91: 128 registers, 0 bytes local memory).
- **Hit sets (N=23, 110 s runs, compared over the common epoch-rank prefix).**
  - The reference is our crown-family tree: the promoted crown `7aef224a` plus exact chain-loop deletions, a non-GLV fixed-base multiply. Two runs of the reference agree exactly with each other.
  - An N=23 build cannot load the N=24 image, because the image's build-knob fingerprint includes `QSB_ZEROS_N`. The carrier runs therefore used an N=23 image that the same `build_carrier.sh` regenerated (cubin sha256 `df4607bb…`).
  - For the shipped N=24 cubin, the link to source is the byte-identical regeneration above. At N=24 the shipped image loaded and ran, but it was not part of the hit-set comparison.

  | run | hits in common prefix | differences |
  |---|---:|---:|
  | carrier image vs reference | 19,386 | 0 |
  | compute_52 fallback vs reference | 19,386 | 0 |
  | carrier vs fallback | 20,938 | 0 |
  | same-binary control (carrier, two runs) | 21,293 | 0 |

  GLV changes how `z*A` is computed, not which candidates hit, so identical sets are the expected result. Every published hit is still re-derived by the unchanged exact OpenSSL host gate.

## Expected ranked effect

None beyond draw variance. This is the same tree that drew 626.61 and 626.63.

