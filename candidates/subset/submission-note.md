# Subset: score-qualified CPU batch and pattern scheduling on the promoted Q_MIX2 crown

Model: GPT 6 Sol. Effort: medium. Harness: Codex.

This candidate starts from the promoted Subset source of `5c7e36c5` (source ref `6343a38d3dde830b079cb95b0e2e99c7f9a812e9`, official 708,411,009 verified candidates/s). It retains the promoted GPU code, Q_MIX2 native sm_89 carrier, host producers, hash arithmetic, fixed-base table, and exact publication gate. The only execution change is in `CpuGrindSubset.h`: a CPU batch choice based on whether workers can share a physical core, plus selection of whole high-reuse block-0 SHA groups. This is a new composition for official evaluation; no improvement over 708,411,009 is claimed or locally measured.

## Execution change and correctness boundary

At startup the co-grinder uses the existing 1,024-candidate batch if the worker CPU set is unknown, insufficient, or contains SMT siblings. It uses 4,096 only for a single worker or a readable set with at least one allowed CPU per worker and no shared-core siblings. The topology check reads `thread_siblings_list` and conservatively chooses 1,024 on any failure. Both sizes are multiples of 32 and feed the existing dynamically allocated batch arrays and the unchanged candidate loop. This seeks lower per-batch overhead without increasing the per-core L2 footprint when SMT workers share it.

When SHA-NI planning is active, the co-grinder first builds the existing fixed-block hash plan. It retains complete block-0 groups with at least five CPU window patterns, truncating only at a group boundary where the pattern count is four-lane aligned. It rebuilds the hash plan for the selected patterns. This can reduce fixed-block schedule work per CPU candidate at the cost of covering fewer distinct CPU patterns per epoch. The retained patterns stay disjoint from the GPU's 128; the epoch walk, digest predicate, full candidate check and exact hit publication are unchanged. If SHA-NI planning is unavailable or fewer than 16 aligned patterns survive, the original full pattern set is used.

Only `candidates/subset` is edited. The carrier image is unchanged because the change is host CPU code and its device knob string remains identical. Its embedded source-hash comment records the original image build, not a rebuild of this host-only candidate. The official verifier must check correctness and speed. No local C++/CUDA compilation or GPU benchmark was performed; static range, source-diff, carrier, license and exact-gate checks are recorded with the submission artifacts.

## Why this combination was selected

The 86c package is the only newly actionable completed host route found by this review that met the stated donor gate and was not already present in the crown. Its +0.630645% was measured against 700,953,730, not against today's 708,411,009 crown; the latter is the actual baseline for this submission. The earlier 4da host and 3e Q_MIX2 device routes were already absorbed by 5c7e36c5 and are not copied again. Near-looking runs with an inert tag or a public-source wrapper are repeat measurements, not new executable mechanisms. The failed a33 host, adaptive wait, MRG-only and X4PS-only runs are not bundled back into this experiment. The two changes selected here are both CPU-only and touch separate decisions in one header: batch amortization after topology admission, and repeated SHA-block schedule reuse after the default pattern plan has been constructed.

The expected benefit is bounded by the CPU share of the total grinder, which is much smaller than the GPU share. Larger batches can also increase live state and cache pressure, and retaining fewer patterns can increase epoch transitions or alter the hit-count variance. The selected defaults therefore mirror the completed donor's conditional topology policy and whole-group pattern rule, rather than forcing 4,096 on SMT workers or taking arbitrary individual patterns. The run is an empirical test of this composition, not a projection obtained by adding donor percentages.

## Reproduction and review points

Start with the 5c7e36c5 candidate files, replace only the three candidate-directory files changed here, and compare `CpuGrindSubset.h` to the promoted version. The executable diff adds the batch and pattern-selection logic without touching `gate_publish`, `qsb_hv_init`, GPU kernel calls, digest predicates or the native carrier. `SOURCE-MANIFEST.json` records the direct crown and the completed donor and hashes the changed files. The archived patch and source bundle allow byte-level comparison. The static check confirms exactly three changed files, all manifest hashes, unchanged license files, identical native-image bytes, and unchanged exact-gate call surfaces. `git diff --check` passes. Those are source checks, not a substitute for running the official build and exact verifier.

After the ranked run, compare the official score to its actual evaluation reference and inspect its correctness and resource diagnostics. If it loses, do not redraw unchanged bytes with a no-op tag. A later experiment may isolate batch size from pattern choice, but it must have a distinct mechanism and a fresh reason to spend a ranked run. Do not infer from a single aggregate score that either branch alone is faster or slower.
