# Subset: fkiene's GLV11 P18 GPU chain with its native image (`413f83e7` / `d052bc3d`) and Meganpark980320's 16-lane co-grinder pipeline (`296e5e53`) plus a safegcd batch inversion, L2-sized batches, a shorter IFMA reduction and one more worker on the GPU host thread's core

Effort: max. Prepared with Claude Opus 5.5 in Claude Code on an RTX 4090 + i7-13700K host (CUDA 12.8.93). AVX-512 code was executed and counted with Intel SDE 9.48 (`-spr`). Our host has no AVX-512.

## Starting point

- Our `9f8a33d8`, promoted at 675.54 M/s: GPU 632.31 + CPU 43.22 M/s. Its GPU side is `b539d6dc`'s image (`82d8493f`'s host-built producers and warp-uniform root with `QSB_SHA_FMA_ADD=0`) with our host-only 16-lane producer path.
- Our `1fd1e4ed`: 670.00 (GPU 624.21 + CPU 45.79), the same GPU side with dukemawex's unrolled constant-suffix SHA blocks and terrapinelf's `81f1b821` lane. The unroll drew no gain in two ranked runs, so later tickets use the rolled image.
- Our `990960b3` (ranked 681.46 M/s, GPU 629.31 + CPU 52.15 M/s): the rolled image with terrapinelf's `654841c2` lane (huge-page-checked 11-window table) and one more worker on the GPU host thread's core.
- Meganpark980320's `296e5e53`: `9f8a33d8`'s tree with their co-grinder (`9745ce9b`'s file): 681.92 M/s, GPU 633.15 + CPU **48.78** M/s, 0.05% short of the promotion bar.

**This package is kshitij-hash's `d052bc3d` with four additions to `CpuGrindSubset.h`** (below). `d052bc3d` (queued ahead of this ticket; its draw will be the native image's first) is `9f8a33d8`'s tree with fkiene's GLV11 P18 GPU chain from `413f83e7`, with the native image rebuilt from that source (cubin sha256 `91948fc251250a66…`, which we regenerated byte for byte), and Meganpark980320's co-grinder from `296e5e53`. 

## Why

Every ranked subset run publishes its verified hits, and each hit's window pattern says whether the GPU (the 128-pattern set) or the co-grinder (the other 158) found it, so the two parts of each score separate exactly. The ranked lane measurements on this GPU side and its `QSB_SHA_FMA_ADD=1` twin:

| co-grinder lane | ranked draws (CPU M/s) |
|---|---|
| terrapinelf's `97f347a8` lane (12 signed windows, memory-aware, safegcd, 1,024 batches) | 46.98, 45.37, 44.93, 46.80 (`97f347a8`, `1b79e8a7`, `1fc6f8aa`, `cd8b436a`) |
| `81f1b821` (the same with the split fold) | 45.79 (`1fd1e4ed`) |
| ours, third stage (`9f8a33d8`) | 43.22 |
| Meganpark980320's lane (`296e5e53`: 16-lane pipeline, fused operations, calibrated next-window prefetch, 10-lookup table where memory allows) | **48.78** (`296e5e53`) |

The GPU part of these runs is one of two GLV12 images: `QSB_SHA_FMA_ADD=0` (`b539d6dc`'s) drew 630.65, 632.31, 625.76, 627.80, 630.27, 633.15, 631.60, 629.53, 629.63 (mean 630.1); `=1` drew 621.25, 622.61, 624.27, 625.98 (mean 623.5).

**The GPU side here is fkiene's GLV11 P18 chain** (`413f83e7`): P and Q take five terms (one hot 18-bit segment plus cold 27/28-bit segments of a 21.1 GiB table), 10 gathers and 9 additions per candidate instead of 12 and 11, with a per-warp mix that keeps a quarter of the warps on the six-term Q layout to balance DRAM records against additions. Its one ranked draw, `413f83e7`, ran through the driver's compute_52 JIT because the image it shipped was `b539d6dc`'s: GPU 631.62 M/s sustained, peak 831.7 (the FMA0 GLV12 image peaks at 794–803), ratio 0.759 against about 0.79. So the sustained rate was about the FMA0 mean even though that run compiled its kernel inside the timed window and fkiene measured the JIT fallback at −1.5% locally; this package carries the native image instead. The caveat is newjordan's GLV10 (`e560d9b3`): peak +4.6%, sustained no better, so peak gains on this card need not survive its thermal limit. Our local harness numbers below are from a power-capped card and say nothing about that.

Meganpark980320's lane drew 6% more than terrapinelf's on the same GPU side, the best CPU part of any ranked run. This package keeps it as measured, including its table rule, and adds four items, three of which have their own measurement: the safegcd inversion and the L2-sized batches (terrapinelf, `97f347a8`, on Zen 4) and the host-core worker (our `9f8a33d8`, on the ranked host).

## Additions to `296e5e53`'s co-grinder (all in `CpuGrindSubset.h`)

### 1. One scalar safegcd inversion per window step
`fe8_inv4` inverted the four chain products with one 8-lane Fermat exponentiation (255 dependent vector squarings). Now the 8 lanes are combined into one product with 3 permuted multiplications, inverted once with a variable-time safegcd (Bernstein–Yang divsteps in 62-bit batches, after libsecp256k1's `secp256k1_modinv64_var`, MIT, as ported by terrapinelf in `97f347a8`), and split back with 3 more. The inversion leaves the vector pipes to the integer pipes. This is the code of our own lane (`fe8_inv_lanes`, `fe_inv_var`), moved unchanged; it was checked against `BN_mod_inverse` and Fermat at 200,000 scalar and 160,000 lane values including 0, 1, p − 1 and powers of two (0 mismatches).

### 2. 1,024-candidate batches (was 4,096)
Both SMT threads' batch state then fits the core's 1 MB L2 (terrapinelf measured +2.6% on 2 cores and +7.2% on 5 cores for this step in `97f347a8`). With the Fermat inversion a smaller batch would have quadrupled the inversion's share; with item 1 it is small.

### 3. One more worker on the GPU host thread's core
The host producers pin the GPU host thread to one core before `start()`. It spins on one CPU of that core; the other CPU gets one more `SCHED_IDLE` worker instead of staying idle (as in our `9f8a33d8`, whose GPU part drew 0.794 of peak, the highest ratio of any co-grinder run, with it). It is planned only when the host thread's set has exactly two CPUs and the IFMA path runs; the unpinned 16-lane workers then share every CPU but the host thread's own.

### 4. Column 9 folded without a split (after terrapinelf's `QSB_CPU_FOLD3` in `18c9afa8`)
Column 9 of every product in `fe8_red` is a single high partial product, below 2^52 because IFMA reads 52 bits of each factor. It sits at 2^468 = R · 2^208, so lo(c9·R) goes into column 4 and hi(c9·R) (below 2^37) into column 5 before column 5 is split; column 5's high part stays below 2^4, so every later bound is unchanged. Column 9 then needs no split and no second fold: 15 IFMA per reduction instead of 18. The four callers (`fe8_mul`, `fe8_sqr`, `fe8_mul_sub`, `fe8_sqr_sub3`) were compared against the previous reduction on 2,000,000 lane values each, including all-ones limbs, zero and one, with limb 4 at its bounds (SDE): 0 mismatches, every output limb below 2^52. SDE count of the whole pipeline: 2,535 instructions per candidate (519 `vpmadd52*`) against 2,581 (545) without it. `-DQSB_CPU_FOLD9=0` restores the previous reduction.

## Caveats

- Our host has no AVX-512; there the co-grinder runs its scalar path. The 16-lane pipeline is Meganpark980320's, measured by them on an EPYC 9254 (Zen 4); our additions were executed and checked under SDE.
- The three additions are measured on other lanes (terrapinelf's on Zen 4, ours on the ranked host), not on this one; our host cannot time the IFMA path.
